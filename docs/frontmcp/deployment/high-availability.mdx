FrontMCP supports multi-pod deployments where any pod can receive any request of an MCP session:

- A request for a session another **live** pod owns is relayed to that pod over Redis Pub/Sub, served there, and its response streamed back.
- A request for a session whose owner **stopped** is served by the receiving pod, which takes the session over: surviving pods detect the failure via Redis heartbeat keys and atomically claim orphaned sessions using a Lua CAS (compare-and-swap) script.

## Quick Start

Enable distributed mode with Redis:

```typescript
@FrontMcp({
  info: { name: 'my-server', version: '1.0.0' },
  apps: [MyApp],
  redis: { provider: 'redis', host: 'redis', port: 6379 },
  transport: {
    persistence: {
      redis: { provider: 'redis', host: 'redis', port: 6379 },
    },
  },
})
```

Set the deployment mode and build:

```bash
export FRONTMCP_DEPLOYMENT_MODE=distributed
frontmcp build --target distributed
```

Give every pod the same `MCP_SESSION_SECRET`. Session ids are encrypted with it, so a pod running with a different secret (or none — each pod then falls back to its own machine id) answers another pod's sessions with `404` and the client re-initializes. See [Running more than one instance](/frontmcp/deployment/redis-setup#running-more-than-one-instance).

## Architecture

The HA module has four components that work together:

### Heartbeat Service

Each pod writes a heartbeat key to Redis every 10 seconds with a 30-second TTL. When a pod dies, its key expires automatically.

```
Key:   mcp:ha:heartbeat:{nodeId}
TTL:   30,000ms (PX)
Value: { nodeId, startedAt, lastBeat, sessionCount }
```

Other pods check for heartbeat presence before relaying to a pod or taking over its sessions. While a pod's heartbeat key exists it is alive; once the key is missing, the owning pod is presumed dead.

### Request Relay

Each session's owner is recorded on the transport bus (`mcp:bus:session:{sessionId}`, a hash with the owning `nodeId`, its relay channel, and the session's transport type and token hash), and in the persisted session record (`transport.persistence`). A pod that receives a request for a session it does not hold:

1. Looks up the owner — in the hookable `relayToSessionOwner` stage of the `http:request` flow, which runs right after the IP filter and **before** quota and authentication. Only a session id this deployment minted (it decrypts under `MCP_SESSION_SECRET`) is looked up; any other id costs no Redis round trip and is answered by the receiving pod.
2. If the owner is **another live pod**, publishes the request (method, URL, headers, parsed body, client address) to that pod's channel `mcp:ha:notify:{nodeId}`.
3. The owner runs the request through its own `http:request` flow — IP filter, quota, session verification, routing, the MCP transport, audit and every hook run there, exactly as for a request it received itself — and publishes what it writes (status, headers, each body chunk, end) back to the relaying pod, which streams it to the client. SSE responses and the standalone `GET` notification stream are streamed chunk by chunk.

If the client disconnects, the relaying pod tells the owner to abort the request. If the owner does not listen on its channel, does not acknowledge the request within 5 seconds, its heartbeat expires while it serves, or nothing arrives from it for three heartbeat intervals (the owner sends a keepalive frame while a response, such as an SSE stream, is quiet), the client gets `503` with a `Retry-After` of the heartbeat TTL (see [Errors](#errors)) instead of a broken session — or, when part of the response already reached the client, the response is ended: the stopped pod's heartbeat expires within that time, and the retry takes the session over. A response frame the owner cannot publish (Redis error, or the relaying pod no longer listens) aborts the response on the owner and ends it on the relaying pod, so a response missing a chunk is never completed. A relayed request is never relayed again.

<Note>
  The owner trusts what arrives on its relay channel like any other request: it re-authenticates it. Run Redis on a private network, as for the session store — anyone who can publish to Redis can inject requests, just as anyone who can write to it can rewrite sessions.
</Note>

### Session Takeover

When a request arrives for a session owned by a dead pod, the receiving pod runs an atomic Lua script against Redis:

1. Read the session data
2. Verify the current `nodeId` matches `expectedOldNodeId` (the dead pod)
3. Atomically update `nodeId` to the new pod and set `reassignedAt` / `reassignedFrom`
4. Return success or failure

This CAS operation prevents two pods from claiming the same session simultaneously. The winner recreates the transport from the persisted session (client capabilities included, `reassignedAt` / `reassignedFrom` kept), records itself as the owner on the transport bus, and serves the request. A pod that loses the race relays the request to the winner.

A pod cut off from Redis for longer than the heartbeat TTL may lose its sessions this way while it still holds their transports. Once its heartbeat has lapsed, it re-reads a held session's persisted record before serving it again (once per lapse): if another pod owns the session now, it drops its own transport — leaving the record to the new owner — and relays the request there. While Redis stays unreachable it keeps serving the sessions it holds, since it can neither check nor relay; a client that still reaches it during the partition keeps the old copy until then.

Only Streamable HTTP sessions can be taken over: the transport is recreated from `transport.persistence`, so takeover needs a persistence backend. Without one, a session whose pod stopped is unknown to the others and the client re-initializes.

A session its client ended with `DELETE` is removed from `transport.persistence` as well, public and anonymous sessions included, so neither a restart nor a takeover brings it back. Up to 1.9.1 a public session's transport and stored record stayed in place.

### Notification Relay

MCP notifications (resource updates, list changes) targeting sessions on other pods are relayed over the same channel:

- Each pod subscribes to `mcp:ha:notify:{nodeId}`
- When a notification targets a session on another pod, it is published to the channel of the pod that owns the session (looked up on the transport bus)
- The receiving pod delivers the notification to the local transport; a notification for a session it no longer serves is dropped, never relayed again

```typescript
// Notification relay message
{
  kind: 'notification';
  sessionId: string;
  notification: { method: string; params?: Record<string, unknown> };
  sourceNodeId: string;
  timestamp: number;
}
```

Notifications a tool sends while it runs (progress, logging) travel on the response of its own request, so they reach the client through the request relay.

## Configuration

Configure HA settings via `frontmcp.config.ts`. `frontmcp build --target distributed` writes the `ha` block to the `FRONTMCP_HA_*` variables in the generated setup file (each one only when the platform has not set it), and every pod reads them at startup — so you can also set the variables directly on the pods:

```typescript
import { defineConfig } from 'frontmcp';

export default defineConfig({
  name: 'my-server',
  deployments: [{
    target: 'distributed',
    ha: {
      heartbeatIntervalMs: 5000,
      heartbeatTtlMs: 15000,
      takeoverGracePeriodMs: 3000,
      redisKeyPrefix: 'mcp:ha:',
    },
  }],
});
```

| Field                   | Environment variable                | Type   | Default   | Description                                     |
| ----------------------- | ----------------------------------- | ------ | --------- | ----------------------------------------------- |
| `heartbeatIntervalMs`   | `FRONTMCP_HA_HEARTBEAT_INTERVAL_MS` | number | 10000     | How often each pod writes its heartbeat         |
| `heartbeatTtlMs`        | `FRONTMCP_HA_HEARTBEAT_TTL_MS`      | number | 30000     | TTL for heartbeat key (should be 2-3x interval) |
| `takeoverGracePeriodMs` | `FRONTMCP_HA_TAKEOVER_GRACE_MS`     | number | 5000      | Wait time before claiming orphaned sessions     |
| `redisKeyPrefix`        | `FRONTMCP_HA_KEY_PREFIX`            | string | `mcp:ha:` | Redis key prefix for all HA keys                |

`heartbeatTtlMs` is also how long a request for a stopped pod's session is answered with `503` before another pod takes the session over (`Retry-After` tells the client). Invalid values are ignored and the default applies.

<Tip>
  Set `heartbeatTtlMs` to at least 2x `heartbeatIntervalMs` to avoid false positives from network jitter.
</Tip>

## Orphan Session Scanner

In addition to on-demand session takeover (when a request arrives for a dead pod's session), FrontMCP runs a periodic **orphan scanner** that proactively detects and claims sessions from dead pods:

1. Runs every heartbeat interval (default: 10s)
2. Compares all session `nodeId` values against alive heartbeat keys
3. Claims orphaned sessions via the same atomic Lua CAS script
4. Records the claiming pod as the session's owner on the transport bus (logged at INFO level), so every pod relays the session's next requests to it; the claiming pod recreates the transport from the persisted session on the first one

The scanner starts automatically in distributed mode when sessions are persisted to Redis (`transport.persistence.redis`) — no other configuration needed. It scans the same key prefix the session store writes to (`<keyPrefix>session:`, default `mcp:session:` — `keyPrefix` defaults to `mcp:`), so a custom `keyPrefix` is honoured. The first scan runs after one full heartbeat interval plus the grace period to allow the cluster to stabilize.

## Redis Connection

The heartbeat, takeover, transport bus and relay publishing share one dedicated ioredis client built from your top-level `redis` config (`host`, `port`, `password`, `db`, `tls`, or `url`); a second connection holds the subscription to the pod's relay channel (a subscribed Redis connection runs no other commands). Both reconnect automatically, log connection errors at a rate-limited interval instead of on every retry, and are closed on shutdown. If the subscription cannot be made at startup it is retried with exponential backoff (1s doubling to 30s); until it succeeds the pod serves its own sessions and answers requests for other pods' sessions with `503`. Vercel KV (`provider: 'vercel-kv'`) is REST-only and cannot provide the Lua/pub-sub primitives HA needs, so distributed mode starts without HA when it is configured.

## Session TTL

Persisted sessions expire after the first of these that is set:

1. `transport.persistence.defaultTtlMs`
2. `transport.persistence.redis.defaultTtlMs`
3. 1 hour (`3600000`)

The TTL slides: the pod serving a session refreshes it while requests keep arriving, at most once per quarter of the TTL per session, so an active session does not expire under the pod that owns it.

```typescript
@FrontMcp({
  redis: { host: process.env.REDIS_HOST ?? 'localhost', port: 6379 },
  transport: {
    persistence: { redis: { host: process.env.REDIS_HOST ?? 'localhost', defaultTtlMs: 30 * 60_000 } },
  },
})
```

## Redis Unavailable at Startup

If Redis cannot be reached while the server starts, session persistence is disabled for the moment and the server starts. The connection is then retried in the background with exponential backoff (1s doubling to 30s) until it succeeds, after which sessions are persisted and `/readyz` reports ready. No restart is needed.

## Load Balancer Affinity

FrontMCP sets two identifiers on both Streamable HTTP and SSE responses for load balancer routing:

- **Cookie**: `__frontmcp_node` --- set during the initialize handshake. Its name, `Domain` and `SameSite` come from the deployment's [`server.cookies`](/frontmcp/deployment/frontmcp-config#cookie-options) (`affinity`, `domain`, `sameSite`) — keep the load balancer's cookie name in step with `affinity`
- **Header**: `X-FrontMCP-Machine-Id` --- set on every response in distributed mode (`FRONTMCP_DEPLOYMENT_MODE=distributed`, which `frontmcp build --target distributed` sets): initialize, message POSTs, DELETE, stateless and MCP 2026-07-28 requests, SSE, `/healthz`, `/readyz`, `/metrics` and 404s. The host adapters (Express and the web-fetch handler) add it where they add the security headers, so no response path misses it; the streamable-HTTP and stateless flows also set it in a hookable `applyNodeHeaders` stage, so plugins can observe or wrap it. Standalone and serverless instances do not send it.

### NGINX Sticky Sessions

```nginx
upstream mcp_backend {
    hash $cookie___frontmcp_node consistent;
    server pod-1:3000;
    server pod-2:3000;
    server pod-3:3000;
}

server {
    location / {
        proxy_pass http://mcp_backend;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

<Note>
  Affinity is an optimization, not a requirement: without it (plain round-robin), a request that lands on another pod is relayed to the session's owner, at the cost of one Redis round trip each way. With it, requests reach the owner directly and relays happen only after a failover. If the pod dies, the load balancer routes to a different pod, which takes the session over.
</Note>

### SSE-Specific Routing

SSE (Server-Sent Events) requires special attention because the `/sse` endpoint creates a long-lived connection. POST requests to `/message` **must** reach the pod with the active SSE stream.

FrontMCP handles this in two layers:

1. **LB Affinity (primary)**: The `__frontmcp_node` cookie is set during SSE initialization, so the load balancer routes subsequent POST requests to the correct pod.
2. **Request Relay (fallback)**: If a POST arrives at the wrong pod, it is relayed to the pod holding the SSE stream, which handles the message and answers through that stream.

<Warning>
  Unlike Streamable HTTP sessions, SSE sessions **cannot be recreated** on a different pod because the SSE response stream is tied to the original HTTP connection. If the owning pod dies, the client must re-establish the SSE connection on a new pod.
</Warning>

For NGINX, enable sticky sessions via the affinity cookie and ensure long-lived connections are supported:

```nginx
server {
    location /sse {
        proxy_pass http://mcp_backend;
        proxy_http_version 1.1;
        proxy_set_header Connection '';
        proxy_buffering off;
        proxy_cache off;
        proxy_read_timeout 86400s;
    }
}
```

## Kubernetes

Deploy with 3 replicas and a Redis instance:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: mcp-server
spec:
  replicas: 3
  selector:
    matchLabels:
      app: mcp-server
  template:
    metadata:
      labels:
        app: mcp-server
    spec:
      containers:
        - name: mcp-server
          image: my-registry/mcp-server:latest
          env:
            - name: FRONTMCP_DEPLOYMENT_MODE
              value: distributed
            - name: REDIS_HOST
              value: redis
          ports:
            - containerPort: 3000
          livenessProbe:
            httpGet:
              path: /healthz
              port: 3000
            initialDelaySeconds: 5
            periodSeconds: 10
          readinessProbe:
            httpGet:
              path: /readyz
              port: 3000
            initialDelaySeconds: 10
            periodSeconds: 15
---
apiVersion: v1
kind: Service
metadata:
  name: redis
spec:
  selector:
    app: redis
  ports:
    - port: 6379
```

<Warning>
  Each pod gets its machine ID from the Kubernetes `HOSTNAME` environment variable (set to the pod name automatically). Do not override `HOSTNAME` in your deployment spec.
</Warning>

## Errors

| Error                          | When                                                                                                                                       | Action                                                                                                       |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------ |
| `SessionOwnerUnreachableError` | `503` with `Retry-After`: the session's owner is alive by its heartbeat but did not answer the relayed request (typically it just stopped) | Retry after `Retry-After` seconds — by then the owner answers again or its session is taken over             |
| `SessionClaimConflictError`    | Another pod claimed the session and is gone too, or the session expired meanwhile (logged; the client gets `404` and re-initializes)       | None — a pod that loses a takeover race to a live pod relays the request to it instead of raising this error |
| `HaConfigurationError`         | Redis not configured but `FRONTMCP_DEPLOYMENT_MODE=distributed`                                                                            | Add `redis` configuration to `@FrontMcp()` decorator                                                         |

The JSON-RPC body of the `503`:

```json
{
  "jsonrpc": "2.0",
  "id": 7,
  "error": {
    "code": -32000,
    "message": "This MCP session is served by another instance of the server, which did not answer the relayed request. Retry after 30s; if that instance has stopped, the session is taken over by another instance once its heartbeat expires."
  }
}
```

## Verifying HA

```bash
# Check heartbeat keys
redis-cli KEYS "mcp:ha:heartbeat:*"

# Inspect a heartbeat value
redis-cli GET "mcp:ha:heartbeat:mcp-server-7b8f9-abc12"

# Which pod owns a session (transport bus)
redis-cli HGETALL "mcp:bus:session:<mcp-session-id>"

# Every pod listens on its relay channel
redis-cli PUBSUB CHANNELS "mcp:ha:notify:*"

# Watch session takeover in real time
redis-cli MONITOR | grep "EVAL"
```
