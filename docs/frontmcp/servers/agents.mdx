Agents are **autonomous AI units** that have their own LLM provider, can execute tools, and are themselves callable as tools. They enable sophisticated multi-agent architectures where specialized agents can be composed and orchestrated.

<Info>
Agents build on the MCP Tools specification—each agent is automatically exposed as an `invoke_<agent-id>` tool that any MCP client can call.
Everything the agent declares that gates a tool (`availableWhen`, `rateLimit`, `concurrency`, `timeout`, `authorities`, and plugin fields such as `approval` or `featureFlag`) applies to that tool.
</Info>

<Tip>
**Nx users:** Scaffold with `nx g @frontmcp/nx:agent my-agent --project my-app`. See [Agent Generator](/frontmcp/nx-plugin/generators/agent).
</Tip>

## Why Agents?

In the Model Context Protocol, agents serve a distinct purpose from tools, resources, and prompts:

| Aspect           | Agent                               | Tool                       | Resource         | Prompt                         |
| ---------------- | ----------------------------------- | -------------------------- | ---------------- | ------------------------------ |
| **Purpose**      | Autonomous AI execution             | Execute actions            | Provide data     | Provide templated instructions |
| **Has LLM**      | Yes (own LLM provider)              | No                         | No               | No                             |
| **Direction**    | Model or user triggers execution    | Model triggers execution   | Model pulls data | Model uses messages            |
| **Side effects** | Yes (LLM calls, tool execution)     | Yes (mutations, API calls) | No (read-only)   | No (message generation)        |
| **Use case**     | Complex reasoning, multi-step tasks | Actions, integrations      | Context loading  | Conversation templates         |

Agents are ideal for:

- **Complex reasoning** — tasks requiring multiple LLM calls and tool use
- **Specialized expertise** — domain-specific agents (research, writing, coding)
- **Orchestration** — coordinating multiple sub-agents for complex workflows
- **Isolation** — agents with their own tools, resources, and providers

## Creating Agents

### Class Style (Default Behavior)

The simplest agent requires **no `execute()` method**. The default behavior automatically:

- Runs the execution loop with the LLM
- Connects tools and executes them as needed
- Sends notifications on tool calls and output

```ts
import { Agent, AgentContext } from '@frontmcp/sdk';
import { z } from '@frontmcp/sdk';

@Agent({
  name: 'research-agent',
  description: 'Researches topics and compiles summaries',
  systemInstructions: 'You are a research assistant. Search for information and provide concise summaries.',
  inputSchema: {
    topic: z.string().describe('Topic to research'),
  },
  llm: {
    provider: 'openai',
    model: 'gpt-4o',
    apiKey: { env: 'OPENAI_API_KEY' },
  },
  tools: [WebSearchTool, SummarizeTool],
})
class ResearchAgent extends AgentContext {}  // No execute() needed!
```

### Class Style (Custom Behavior)

Override `execute()` only when you need custom pre/post processing:

```ts
@Agent({
  name: 'custom-agent',
  description: 'Agent with custom logic',
  systemInstructions: 'You are a helpful assistant.',
  inputSchema: {
    query: z.string(),
  },
  llm: {
    provider: 'openai',
    model: 'gpt-4o',
    apiKey: { env: 'OPENAI_API_KEY' },
  },
})
class CustomAgent extends AgentContext {
  async execute(input: { query: string }) {
    // Custom pre-processing
    this.notify('Starting custom processing...', 'info');

    // Call the default agent loop
    const result = await super.execute(input);

    // Custom post-processing
    return { ...result, customField: 'added' };
  }
}
```

### Function Style

For simpler agents, use the functional builder. The handler is the agent's `execute()`: it gets the validated input and the agent's context, and what it returns is the agent's output.

```ts
import { agent } from '@frontmcp/sdk';
import { z } from '@frontmcp/sdk';

const EchoAgent = agent({
  name: 'echo-agent',
  description: 'Echoes back the input message',
  inputSchema: {
    message: z.string(),
  },
  llm: {
    provider: 'openai',
    model: 'gpt-4o-mini',
    apiKey: { env: 'OPENAI_API_KEY' },
  },
})(({ message }) => ({ echoed: `Echo: ${message}` }));
```

<Note>
Up to 1.8.7 the handler never ran: every call failed output validation with a list of Zod issues.
</Note>

### The Agent's Options

Inside the agent (a class's `execute()`, or the context a function agent's handler gets), the options given to `@Agent` are `this.metadata`, with their defaults applied: `this.metadata.swarm`, `this.metadata.execution?.maxIterations`, and so on.

### Invocation, Hooks and Request Context

Calling `invoke_<agent-id>` runs two flows:

1. `tools:call-tool` for the agent's tool, which applies everything the agent declares: `authorities`, `rateLimit`, `concurrency`, `timeout`, and plugin fields such as `approval` or `featureFlag`.
2. `agents:call-agent`, which runs the agent. Hooks registered for agent invocation run here: `AgentCallHook` in a plugin, or `@AgentCallHook.Will(...)` / `.Did(...)` methods on the agent class itself.

Inside the agent, including a custom `execute()`, `this.context` (request id, session, auth info) and `CONTEXT`-scoped providers are available, as in a tool.

## Registering Agents

Add agents to your app via the `agents` array:

```ts
import { App } from '@frontmcp/sdk';

@App({
  id: 'my-app',
  name: 'My Application',
  agents: [ResearchAgent, CalculatorAgent, WriterAgent],
})
class MyApp {}
```

Each agent is automatically exposed as a tool:

- `invoke_research-agent`
- `invoke_calculator-agent`
- `invoke_writer-agent`

### Agents from npm or Remote Servers

`Agent.esm()` and `Agent.remote()` exist, but startup refuses them: per-entry `.esm()` and `.remote()` loading covers tools, resources and prompts only. An `agents` array that lists one fails startup with `ExternalEntryNotSupportedError`, naming the agent and its source:

```text
Agent "writer" from @acme/agents@^1.0.0 is not supported: per-entry .esm() and .remote() loading is supported for tools, resources and prompts only; declare the agent with @Agent() or agent() instead
```

Use one of these instead:

- **Declare the agent locally** with `@Agent()` or `agent()`. Its `tools` can include [`Tool.esm()` and `Tool.remote()`](/frontmcp/servers/tools#loading-from-npm-or-remote-servers) entries, so the agent can use tools from a package or another server.
- **Call an agent another FrontMCP server hosts** through the `invoke_<agent>` tool that server exposes for it, e.g. `Tool.remote('https://agents.example.com/mcp', 'invoke_writer')`, or proxy the whole server with [`App.remote()`](/frontmcp/servers/apps#remote-apps).

## LLM Configuration

Agents require an LLM configuration. FrontMCP provides **native adapters** for OpenAI and Anthropic SDKs with built-in retry logic, streaming support, and token tracking.

### Built-in Providers (Shorthand)

The simplest way to configure an LLM — the SDK auto-creates the appropriate adapter:

```bash
# For OpenAI
npm install openai

# For Anthropic
npm install @anthropic-ai/sdk
```

```ts
@Agent({
  name: 'research-agent',
  llm: {
    provider: 'openai',
    model: 'gpt-4o',
    apiKey: { env: 'OPENAI_API_KEY' },
  },
  // ...
})
class ResearchAgent extends AgentContext {}

@Agent({
```

### OpenAI Adapter (Direct)

For full control, use `OpenAIAdapter` directly. Supports the **Chat Completions API** (default) and the **Responses API**:

```ts
import { OpenAIAdapter } from '@frontmcp/sdk';

// Chat Completions API (default)
const chatAdapter = new OpenAIAdapter({
  model: 'gpt-4o',
  apiKey: process.env.OPENAI_API_KEY,
});

// Responses API
const responsesAdapter = new OpenAIAdapter({
  model: 'gpt-4o',
  apiKey: process.env.OPENAI_API_KEY,
  api: 'responses',
});

// Pre-configured client
import OpenAI from 'openai';
const clientAdapter = new OpenAIAdapter({
  model: 'gpt-4o',
  client: new OpenAI({ apiKey: process.env.OPENAI_API_KEY }),
});

@Agent({
  name: 'research-agent',
  llm: { adapter: chatAdapter },
  // ...
})
class ResearchAgent extends AgentContext {}
```

### Custom Adapter

Implement `AgentLlmAdapter` for any other provider:

```ts
import { AgentLlmAdapter, AgentCompletion, AgentPrompt, AgentToolDefinition } from '@frontmcp/sdk';

const myAdapter: AgentLlmAdapter = {
  async completion(prompt: AgentPrompt, tools?: AgentToolDefinition[]): Promise<AgentCompletion> {
    const response = await myLlmClient.chat({
      messages: prompt.messages,
      system: prompt.system,
      tools: tools?.map(t => ({ name: t.name, description: t.description })),
    });

    return {
      content: response.text,
      finishReason: response.hasToolCalls ? 'tool_calls' : 'stop',
      toolCalls: response.toolCalls,
    };
  },
};

@Agent({
  name: 'custom-agent',
  llm: { adapter: myAdapter },
})
class CustomAgent extends AgentContext {}
```

## Agent-Scoped Components

Agents can have their own isolated tools, resources, prompts, and providers:

```ts
@Agent({
  name: 'isolated-agent',
  description: 'Agent with its own scope',

  // Agent-scoped tools (only this agent can use them)
  tools: [PrivateTool],

  // Agent-scoped resources
  resources: [AgentConfig],

  // Agent-scoped prompts
  prompts: [AgentInstructions],

  // Agent-scoped providers
  providers: [DatabaseService],

  // Shared with the app
  exports: { resources: [AgentConfig], prompts: '*', providers: [DatabaseService] },

  llm: { ... },
})
class IsolatedAgent extends AgentContext { ... }
```

| Option      | Who sees it                                                                                                                                                                                    |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `tools`     | The agent's model, which is offered them as tools. Clients aren't.                                                                                                                             |
| `providers` | The agent's tools (`this.get(DatabaseService)`). They don't have to be registered in the app too: up to 1.8.7 an agent provider the app didn't also register stopped the server from starting. |
| `resources` | Nobody, unless exported: the agent's model is sent tools only. A resource that isn't exported is reported at startup.                                                                          |
| `prompts`   | Nobody, unless exported, as for resources.                                                                                                                                                     |
| `agents`    | The agent's model (see [Nested Agents](#nested-agents)).                                                                                                                                       |

The agent's tools also see the providers of the agent's app and of the server, as the app's own tools do (for a nested agent, those of its parent agent too). Up to 1.9.1 an app provider failed in an agent's tool with `Provider "TicketStore" is not available`; only server-level providers reached it.

From the agent's own code, `this.callTool(name, args)` reaches the agent's own tools and its nested agents' `invoke_<agent-id>` tools, which run in the agent's scope, and otherwise the tools of the server. Up to 1.9.1 it found only the server's tools, so a call to one of the agent's own tools or nested agents answered `Tool not found`.

### Exports

`exports` shares some of the agent's own entries with the scope it is registered in (the server, or its parent agent for a nested agent):

- `resources` (a list, or `'*'` for all of them): listed in `resources/list` and read with `resources/read` like the app's own.
- `prompts` (a list, or `'*'`): listed in `prompts/list` and got with `prompts/get`.
- `providers`: the app's tools, resources and prompts can inject them.

Each export must be one of the agent's own `resources`, `prompts` or `providers`; otherwise the server refuses to start with `AgentConfigurationError` (`Agent "isolated-agent" exports prompts "X", which is not one of its own prompts`). Any other key, such as `exports: { tools }`, is refused when the agent is decorated. Up to 1.8.7 nothing was exported.

## Swarm Configuration

Control agent visibility for multi-agent coordination:

```ts
@Agent({
  name: 'orchestrator-agent',
  description: 'Coordinates other agents',
  swarm: {
    canSeeOtherAgents: true,              // Can this agent invoke others?
    visibleAgents: ['worker-a', 'worker-b'], // Which agents can it see?
    isVisible: true,                      // Can other agents see this one?
    maxCallDepth: 3,                      // Max agent-to-agent calls in one chain
  },
  llm: { ... },
})
class OrchestratorAgent extends AgentContext {
  async execute({ task }: { task: string }) {
    // Can invoke visible agents
    const result = await this.invokeAgent('worker-a', { data: task });
    return { orchestrated: result };
  }
}
```

With `canSeeOtherAgents: true`, the agent sees the other agents registered in the same scope: those in `visibleAgents` when it is set, all of them otherwise, never itself and never one with `isVisible: false`.

- Its **model** is offered each agent it sees as that agent's `invoke_<agent-id>` tool, next to its own tools, so the model decides when to delegate.
- **`this.invokeAgent(agentId, input)`** calls an agent it sees, or one of its [nested agents](#nested-agents), and returns that agent's output. `input` is the called agent's arguments object. An agent that exists but isn't seen fails with `AgentVisibilityError` (`AGENT_VISIBILITY_DENIED`), an unknown one with `AgentNotFoundError`.

Either way the call runs through the called agent's `invoke_<agent-id>` tool, so its `authorities`, `rateLimit`, `concurrency`, `timeout` and hooks apply, as for a client's call.

### Call Depth

`maxCallDepth` (1 to 10, default 3) limits how many agent-to-agent calls deep a chain may go: an agent called by a client that calls another makes call 1. It counts every way one agent reaches another: through its model, `this.invokeAgent()`, or `this.callTool('invoke_<agent-id>')`. When several agents are running in the chain, the smallest of their `maxCallDepth` applies, and agents without `swarm` count with the default of 3. It counts calls, not agents: with the default of 3, a chain of four agents runs (the agent the client called, and three agents each called by the one before), and the fifth is refused. A deeper call fails with `AgentCallDepthExceededError` (`AGENT_CALL_DEPTH_EXCEEDED`):

```text
Agent "pong" can't be called from "ping" -> "pong" -> "ping": that would be agent call 3, deeper than maxCallDepth 2
```

<Note>
Up to 1.8.7 `swarm` was accepted and ignored: the model was offered no other agent, `this.invokeAgent()` always threw `Agent method "invokeAgent" is not available`, and nothing limited the depth.
</Note>

### Visibility Patterns

**Orchestrator Pattern** — A central agent coordinates specialized workers:

```ts
// Workers (can't see each other)
@Agent({ name: 'research-worker', swarm: { isVisible: true, canSeeOtherAgents: false }, ... })
class ResearchWorker extends AgentContext { ... }

@Agent({ name: 'writer-worker', swarm: { isVisible: true, canSeeOtherAgents: false }, ... })
class WriterWorker extends AgentContext { ... }

// Orchestrator (can see and invoke workers)
@Agent({
  name: 'orchestrator',
  swarm: { canSeeOtherAgents: true, visibleAgents: ['research-worker', 'writer-worker'] },
  ...
})
class Orchestrator extends AgentContext { ... }
```

## Execution Configuration

Control agent execution behavior:

```ts
@Agent({
  name: 'long-running-agent',
  execution: {
    maxIterations: 10,          // Max tool call rounds (default: 10)
    timeout: 120000,            // Timeout in ms (default: 120000)
    enableNotifications: true,  // Send progress notifications
    enableAutoProgress: false,  // Auto progress during LLM calls (default: false)
    inheritParentTools: false,  // Also offer the model the app's tools (default: false)
    inheritPlugins: false,      // Also run the app's and server's plugins for the agent's tools (default: false)
    useToolFlow: true,          // Execute tools through call-tool flow (default: true)
    notificationInterval: 1000, // Least time between two automatic progress updates in ms (default: 1000)
  },
  llm: { ... },
})
class LongRunningAgent extends AgentContext { ... }
```

### Inheriting the App's Tools

With `inheritParentTools: true`, the model is also offered the tools of the scope the agent is registered in (the server's tools, which include its app's; a nested agent gets its parent agent's), other than agents: which agents it can call is `swarm`'s to decide. Those tools run through that scope's `tools:call-tool` flow, with the hooks and gates that apply there, whatever `useToolFlow` says. Only tools whose `availableWhen.surface` offers them to agents are included, and the agent's own tools win a name clash. By default the model is offered the agent's own tools only.

<Note>
`enableStreaming` is not supported yet: the agent replies once its run completes, and an agent that sets `enableStreaming: true` is reported with a warning at startup. Use `enableAutoProgress` for progress notifications during the run. Up to 1.8.7 `enableStreaming`, `inheritParentTools` and `inheritPlugins` were accepted and ignored, and the documented default of `inheritParentTools` was `true`.
</Note>

### Tool Execution Mode

By default, agents execute tools through the full `call-tool` flow, which includes:

- Plugin hooks (caching, rate limiting, audit logging)
- Authorization checks
- Tool middleware and transformations

The plugin hooks are those of the plugins installed on the agent (`@Agent({ plugins })`), which apply to the agent's own tools the way an app's plugins apply to the app's tools. Plugins on the server or the app don't reach them unless the agent sets `execution.inheritPlugins: true`: its tools then also get the hooks of the plugins installed on its app and on the server, ordered with its own by priority (its own first among equals). A plugin installed both on the agent and above it runs once, as installed on the agent. The startup check for metadata only a plugin enforces (`approval`, `featureFlag`) counts those inherited plugins too: up to 1.9.1 an agent's tool with `approval: true` refused to start with `Unenforced metadata` when `ApprovalPlugin` was installed only on the app, even with `inheritPlugins: true`. Up to 1.8.2, a plugin on an agent with a hook of its own (such as `FeatureFlagPlugin`) made every tool call of that agent fail with `Unsupported hook owner kind: "agent"`.

The agent's own tools also get the `rateLimit`, `concurrency` and `timeout` they declare (else `throttle.defaultRateLimit`, `defaultConcurrency` and `defaultTimeout`), as the app's tools do; a `rateLimit` or `concurrency` there is enforced without a `throttle` option. The calls an agent makes during its run (its model's tool calls, its nested and swarm agents) run inside the `throttle.globalConcurrency` slot of the call that runs the agent. Up to 1.8.7 the `rateLimit` and `concurrency` of an agent's own tools were ignored.

For performance-critical scenarios, you can disable flow execution:

```ts
@Agent({
  name: 'fast-agent',
  execution: {
    useToolFlow: false,  // Direct execution, bypasses plugins
  },
  llm: { ... },
})
class FastAgent extends AgentContext { ... }
```

<Warning>
Setting `useToolFlow: false` bypasses all plugin hooks and middleware, and the tools' `rateLimit`, `concurrency` and `timeout`, for the agent's own tools (their `authorities` still apply). Its [nested agents](#nested-agents) still run through their `invoke_` tool's flow. Only use this when you need maximum performance and don't require plugin features.
</Warning>

## Overriding Behavior

Customize agent behavior by overriding methods in `AgentContext`:

```ts
@Agent({ name: 'custom-agent', llm: { ... } })
class CustomAgent extends AgentContext {
  // Override LLM completion for custom logic
  protected override async completion(prompt, tools, options) {
    this.logger.info('Making LLM request...');
    const result = await super.completion(prompt, tools, options);
    this.logger.info(`LLM returned: ${result.finishReason}`);
    return result;
  }

  // Override tool execution for logging/caching: every tool call of the model goes through it
  protected override async executeTool(name: string, args: Record<string, unknown>) {
    this.logger.info(`Executing tool: ${name}`);
    return super.executeTool(name, args);
  }

  async execute(input: { query: string }) {
    return { result: '...' };
  }
}
```

Every completion of the default loop goes through `completion()`, and every tool call of its model through `executeTool()`. The loop passes `completion()` the agent's completion options: `llm.temperature` and `llm.maxTokens` when the agent's `llm` sets them, else an empty object. Override `completionOptions()` to send others to every completion:

```ts
protected override completionOptions() {
  return { temperature: 0.2, maxTokens: 800 };
}
```

Up to 1.8.7 an `executeTool()` override never saw the model's tool calls, and up to 1.9.1 a `completion()` override never ran: the loop called the adapter directly, with `options` always `undefined`.

## Progress Notifications

Keep users informed during long operations using manual or automatic notifications.

### Manual Notifications

Use `this.notify()` to send custom messages at specific points:

```ts
@Agent({ name: 'notifying-agent', llm: { ... } })
class NotifyingAgent extends AgentContext {
  async execute({ task }: { task: string }) {
    await this.notify('Starting task...', 'info');

    // Step 1
    await this.notify('Gathering data...', 'info');
    const data = await this.gatherData();

    // Step 2
    await this.notify('Processing...', 'info');
    const result = await this.process(data);

    await this.notify('Complete!', 'info');
    return { result };
  }
}
```

Use `this.progress()` for progress bars when the client provides a `progressToken`:

```ts
@Agent({ name: 'progress-agent', llm: { ... } })
class ProgressAgent extends AgentContext {
  async execute({ files }: { files: string[] }) {
    for (let i = 0; i < files.length; i++) {
      await this.progress(i + 1, files.length, `Processing ${files[i]}`);
      await this.processFile(files[i]);
    }
    return { processed: files.length };
  }
}
```

### Automatic Progress (Opt-in)

Enable `enableAutoProgress` to automatically send progress notifications during the agent execution loop:

```ts
@Agent({
  name: 'auto-progress-agent',
  execution: {
    enableAutoProgress: true,  // Opt-in to automatic progress
  },
  llm: { ... },
})
class AutoProgressAgent extends AgentContext { }
```

When enabled, the agent automatically sends progress updates at these lifecycle points:

| Event                 | Progress % | Message Example                                |
| --------------------- | ---------- | ---------------------------------------------- |
| LLM call start        | 0-80%      | "Starting LLM call (iteration 1/10)"           |
| LLM response received | varies     | "LLM response received (500P + 200C tokens)"   |
| Tools identified      | -          | "Identified 2 tool call(s): search, calculate" |
| Tool execution        | varies     | "Executing tool 1/2: search"                   |
| Completion            | 100%       | "Agent completed"                              |

<Info>
Auto progress requires both `enableAutoProgress: true` and `enableNotifications: true` (the default).
Progress notifications are only sent if the client includes a `progressToken` in the request's `_meta` field.
</Info>

`execution.notificationInterval` (default 1000 ms) is the least time between two automatic progress updates: an update that comes sooner is skipped, except the last one (`Agent completed` or `Agent failed: ...`), which is always sent. It doesn't apply to your own `this.progress()` calls.

`this.notify()` and `this.progress()` reach the client the way a tool's do: on a session (where `notifications/message` needs the client to have set a log level with `logging/setLevel`), and under MCP 2026-07-28 on the request's own response stream. Up to 1.9.1 an agent's own `notify()` and `progress()`, and its automatic progress, returned `false` and sent nothing under 2026-07-28, and `notificationInterval` was never read.

## Error Handling

Handle errors gracefully in agents:

```ts
import { AgentExecutionError, AgentTimeoutError } from '@frontmcp/sdk';

@Agent({ name: 'safe-agent', llm: { ... } })
class SafeAgent extends AgentContext {
  async execute(input: { data: string }) {
    try {
      return await this.riskyOperation(input.data);
    } catch (error) {
      if (error instanceof ValidationError) {
        // Return error response with fail()
        this.fail(`Invalid input: ${error.message}`);
      }
      throw error;
    }
  }
}
```

### A tool that fails

When one of the agent's tools fails, the model gets the error as the tool's result, `{"error":"<message>"}`, and decides what to do next. A tool that calls `this.fail(new PublicMcpError('The ticket is locked'))` reaches the model as `{"error":"The ticket is locked"}`. Up to 1.9.1 the message was lost and the model read `{"error":""}`.

### Output that does not match `outputSchema`

An agent's reply is checked against its `outputSchema` exactly as a tool's result is. When it does not match, for example the model answers `{"priority":"urgent"}` for a `z.enum(['low', 'normal', 'high'])` field or replies with text that is not JSON, the call fails with `_meta.code: "INVALID_OUTPUT"` and the message `Tool output validation failed (output does not match outputSchema at priority)`. The result carries no stack trace or server file path.

## Nested Agents

Agents can contain other agents, creating hierarchical structures:

```ts
@Agent({
  name: 'parent-agent',
  description: 'Parent with nested child agents',

  // Nested agents — offered to this agent's model as tools
  agents: [ChildAgentA, ChildAgentB],

  // Parent's own tools
  tools: [PlanningTool],

  llm: { ... },
})
class ParentAgent extends AgentContext {
  async execute({ task }: { task: string }) {
    // The model can call: invoke_child-agent-a, invoke_child-agent-b, planning-tool
    const plan = await super.execute({ task });

    // The agent's own code can call a nested agent too
    const review = await this.invokeAgent('child-agent-b', { plan });
    return { plan, review };
  }
}
```

Nested agents are private to their agent: clients aren't offered their `invoke_` tools. A call to one runs through its `invoke_` tool's `tools:call-tool` flow and then the `agents:call-agent` flow, both in the parent agent's scope, also when the parent sets `execution.useToolFlow: false`: the nested agent's `authorities`, `rateLimit`, `concurrency`, `timeout`, plugin gates and hooks apply as for a client's call, its `exports` reach that scope, and the call counts toward [`maxCallDepth`](#call-depth). A `rateLimit` or `concurrency` declared only on a nested agent is enforced without a `throttle` option, as a tool's is. Under [consent](/frontmcp/authentication/local#consent-and-tool-authorization), the consent given to the agent covers its own tools and nested agents, which the consent screen never offers. Up to 1.8.7 nested agents were created but never offered to the model.
