Apps are the **organizational units** for capabilities in FrontMCP. Each app groups related **tools**, **resources**, and **prompts** into a cohesive domain, along with **providers**, **adapters**, and **plugins** that support them.

## Why Apps?

In FrontMCP, apps provide domain boundaries and enable multi-tenant architectures:

| Aspect       | App                       | Server                 | Tool                 |
| ------------ | ------------------------- | ---------------------- | -------------------- |
| **Purpose**  | Group capabilities        | Host apps              | Execute actions      |
| **Scope**    | Feature/domain boundary   | Process entry point    | Single operation     |
| **Contains** | Tools, resources, prompts | Apps, global providers | Input → Output logic |

Apps are ideal for:

- **Feature domains** — billing, users, analytics as separate concerns
- **Team boundaries** — each team owns their app
- **Multi-tenant** — isolate per customer with `splitByApp: true`
- **Third-party integrations** — wrap OpenAPI adapters per service

---

## Minimal App

```ts
import { App } from '@frontmcp/sdk';

@App({
  id: 'hello',
  name: 'Hello App',
  tools: [],
})
export default class HelloApp {}
```

Add it to your server:

```ts
@FrontMcp({ info: { name: 'Demo', version: '0.1.0' }, apps: [HelloApp] })
export default class Server {}
```

## App options

```ts
@App({
  id?: string,
  name: string,
  description?: string,
  providers?: ProviderType[],
  authProviders?: AuthProviderType[],
  plugins?: PluginType[],
  adapters?: AdapterType[],
  tools?: ToolType[],
  resources?: ResourceType[],
  prompts?: PromptType[],
  auth?: AuthOptions,                 // app auth (see Scoping & auth)
  standalone?: 'includeInParent' | boolean, // isolate scope / expose separately
})
```

**Field descriptions:**

| Field           | Description                                             |
| --------------- | ------------------------------------------------------- |
| `id`            | Unique identifier; used in URLs when `splitByApp: true` |
| `name`          | Human-readable display name                             |
| `description`   | Optional description for documentation                  |
| `providers`     | DI providers scoped to this app                         |
| `authProviders` | Authentication providers for this app                   |
| `plugins`       | Plugins attached at app scope                           |
| `adapters`      | Adapters (e.g., OpenAPI) that generate tools/resources  |
| `tools`         | Tool classes registered to this app                     |
| `resources`     | Resource classes registered to this app                 |
| `prompts`       | Prompt classes registered to this app                   |
| `auth`          | App-level auth config (see _Scoping & auth_ below)      |
| `standalone`    | Isolation mode: `true`, `false`, or `'includeInParent'` |

**Scoping & auth**

- If the server uses **`splitByApp: true`**, each app is isolated and **must** configure its own auth (server-level `auth` is disallowed).
- On the shared endpoint (the default), a server in `local` or `remote` mode federates the app's provider, and checks each tool call against the apps the caller has authorized only when `incrementalAuth` is enabled; without it, app grants are not checked per tool call. A server in `public` or `static` mode refuses to start with a protected app on its shared endpoint, since it would serve that app's tools without the app's auth. The one exception is a `static` app under a `static` server that checks the same header and scheme and accepts every token the server accepts: the server's check then enforces it. To enforce an app's own auth regardless of the server's mode, mark the app `standalone: true` (or use `splitByApp: true`) to give it an endpoint of its own.
- `standalone: true` makes the app expose its own scope/entry; `'includeInParent'` lists it under the parent while keeping isolation.

**Dependency resolution**

- Providers resolve **tool → app → server**.
- Plugins/adapters attach at app scope; generated items inherit the app’s policies and provenance.

## Example: app with adapter + providers

```ts
@App({
  id: 'billing',
  name: 'Billing',
  providers: [DbProvider, CacheProvider],
  adapters: [
    // e.g. OpenAPI adapter that generates tools/resources from a spec
    BillingOpenApiAdapter,
  ],
})
export default class BillingApp {}
```

## Remote Apps

Connect to external MCP servers and proxy their tools, resources, and prompts through your gateway using `App.remote()`:

```ts
import { FrontMcp, App } from '@frontmcp/sdk';

@FrontMcp({
  info: { name: 'Gateway', version: '1.0.0' },
  apps: [
    // Remote MCP server connected via URL
    App.remote('https://mintlify.com/docs/mcp', {
      namespace: 'mintlify', // Tools prefixed as 'mintlify:ToolName'
      transportOptions: {
        timeout: 60000,
        retryAttempts: 2,
      },
    }),
    // Local MCP server on different port
    App.remote('http://localhost:3099/', {
      namespace: 'local',
      transportOptions: {
        timeout: 30000,
        retryAttempts: 3,
      },
    }),
  ],
})
export default class GatewayServer {}
```

### Remote App Options

`App.remote(url, options?)` accepts the MCP server URL as the first argument and an optional options object:

| Option             | Type                           | Description                                                             |
| ------------------ | ------------------------------ | ----------------------------------------------------------------------- |
| `name`             | `string`                       | Override the auto-derived app name (defaults to hostname)               |
| `namespace`        | `string`                       | Prefix for tool/resource/prompt names (e.g., `mintlify:SearchMintlify`) |
| `description`      | `string`                       | Human-readable description                                              |
| `standalone`       | `boolean \| 'includeInParent'` | Isolation mode (default: `false`)                                       |
| `transportOptions` | `object`                       | Connection settings (timeout, retries, headers, MCP revision)           |
| `remoteAuth`       | `RemoteAuthConfig`             | Authentication config for the remote server                             |
| `refreshInterval`  | `number`                       | Interval (ms) to refresh capabilities from the remote server            |
| `cacheTTL`         | `number`                       | TTL (ms) for cached capabilities                                        |
| `filter`           | `AppFilterConfig`              | Include/exclude filter for selectively importing primitives             |

The app's id is its `name`; without one, its `namespace`, else the hostname's first label. Two `App.remote()` or `App.esm()` apps with one id (for example `https://mcp.github.com` and `https://mcp.linear.app`, both `mcp`) stop the server at startup with `DuplicateAppIdError`: give each its own `name` or `namespace`.

### Transport Options

```ts
transportOptions: {
  timeout: 60000,              // Request timeout in milliseconds
  retryAttempts: 2,            // Retries of a tool call that failed with a transient error (default 2, 0 = off)
  retryDelayMs: 1000,          // Delay before the first retry; each later retry waits twice as long
  fallbackToSSE: true,         // Fall back to legacy SSE when Streamable HTTP fails
  headers: { 'x-team': 'a' },  // Sent with every request
  protocolVersion: 'auto',     // 'legacy' (default) | '2026-07-28' | 'auto'
}
```

A transient error is a network failure or timeout, or an HTTP `408`, `425`, `429` or `5xx` answer other than `501` and `505`, whatever its body says; a `400` or `404` is not retried. On a 2026-07-28 remote, a `Retry-After` header on the answer sets the wait, up to the backoff's longest one.

`protocolVersion` selects the MCP revision the gateway speaks to the remote:

- `'legacy'` (or omitted) — the session transports with an `initialize` handshake.
- `'2026-07-28'` — the stateless revision, with no `initialize` and per-request `_meta`. Only for URL
  remotes; any other `urlType` is refused at connect time.
- `'auto'` — probe `server/discover` and use 2026-07-28 when the remote lists it, otherwise fall back to
  the session transports.

See [Protocol versions](/frontmcp/fundamentals/protocol-versions#proxying-a-2026-remote).

Each remote tool, resource, resource template and prompt is listed once. The gateway re-reads the
remote's lists when `cacheTTL` expires (or the remote reports a change), and replaces what it proxied
before: entries the remote dropped disappear, and nothing is listed twice.

### Remote Auth

`remoteAuth` sets the credentials the gateway sends to the remote:

```ts
// The same credentials on every request, discovery included
remoteAuth: { mode: 'static', credentials: { type: 'bearer', value: process.env['UPSTREAM_TOKEN']! } }
// credentials.type: 'bearer' | 'basic' (Authorization header) | 'apiKey' (headerName, default 'X-API-Key')

// The calling user's token, on that user's tool calls, resource reads and prompt requests
remoteAuth: { mode: 'forward' }
remoteAuth: { mode: 'forward', tokenClaim: 'upstream_token', headerName: 'X-Upstream-Auth' }

// No gateway credentials: the remote runs its own OAuth
remoteAuth: { mode: 'oauth' }
```

With `forward`, the gateway sends `Bearer <token>` in `headerName` (default `Authorization`); with
`tokenClaim`, the token is the value of that claim of the caller's JWT instead of the whole token. A call
with no caller token is sent without one. `forward` needs a server (or a standalone app) in `transparent`
mode, whose callers' tokens come from the identity provider: under `public`, `static`, `local` or `remote`
mode the caller's token is one the server minted or holds itself, so startup refuses `forward` there; use
`static` credentials or `transportOptions.headers` instead. Discovery (`tools/list` and the other lists) runs at startup and
on refresh, outside any user's request, so it carries only `transportOptions.headers`: a remote that
requires auth to list its entries needs `static` credentials or a header in `transportOptions.headers`.
A request that carries credentials or `transportOptions.headers` does not follow a redirect: a 3xx from the remote
fails the request rather than sending the credentials on to the origin it names.

### Filtering Remote Entries

`filter` picks which of the remote's entries the gateway proxies, by their names on the remote (before
the namespace prefix). Resource templates are matched under `resources`:

```ts
App.remote('https://api.example.com/mcp', {
  namespace: 'api',
  filter: { exclude: { tools: ['delete_*'] } },                 // everything except these
  // filter: { default: 'exclude', include: { tools: ['search'] } }, // nothing except these
})
```

### Caching Remote Tools

Remote tools don't have cache metadata, so use the `toolPatterns` option in CachePlugin:

```ts
@FrontMcp({
  apps: [
    App.remote('https://api.example.com/mcp', {
      namespace: 'api',
    }),
  ],
  plugins: [
    CachePlugin.init({
      type: 'memory',
      defaultTTL: 300,
      toolPatterns: ['api:*'], // Cache all tools from this namespace
    }),
  ],
})
```

See the [Cache Plugin documentation](/frontmcp/plugins/cache-plugin#caching-remote-tools) for more details on pattern-based caching.

## ESM Package Apps

Load npm packages at runtime and register their tools, resources, and prompts in-process — no HTTP proxy needed — using `App.esm()`:

```ts
import { FrontMcp, App } from '@frontmcp/sdk';

@FrontMcp({
  info: { name: 'Gateway', version: '1.0.0' },
  apps: [
    App.esm('@acme/mcp-tools@^1.0.0', {
      namespace: 'acme',
      autoUpdate: { enabled: true },
    }),
    App.esm('@acme/analytics@^2.0.0', { namespace: 'analytics' }),
  ],
})
export default class Server {}
```

<Info>
Unlike [Remote Apps](#remote-apps) which proxy requests to external MCP servers over HTTP, ESM packages are fetched from a CDN, cached locally, and executed **in-process**. They support two-tier caching, background version polling with hot-reload, and private registry authentication.
</Info>

See the full [ESM Packages reference](/frontmcp/servers/esm-packages) for `App.esm()` API, caching, authentication, and auto-update configuration.

## Per-Primitive Loading

In addition to loading entire apps, you can load **individual tools, resources and prompts** from npm packages or remote servers using the static `.esm()` and `.remote()` methods on `Tool`, `Resource` and `Prompt`:

```ts
import { FrontMcp, App, Tool, Resource, Prompt } from '@frontmcp/sdk';

@App({
  id: 'my-app',
  name: 'My App',
  tools: [
    LocalEchoTool,                                            // Local @Tool class
    Tool.esm('@acme/tools@^1.0.0', 'echo'),                  // Single tool from npm
    Tool.remote('https://api.example.com/mcp', 'search', {    // Proxy single tool from remote
      metadata: { name: 'api_search' },
    }),
  ],
  resources: [
    LocalConfig,
    Resource.esm('@acme/tools@^1.0.0', 'status'),            // Same package: loaded once
  ],
  prompts: [
    Prompt.remote('https://api.example.com/mcp', 'greeting'), // Same server: one connection
  ],
})
class MyApp {}
```

Unlike `App.esm()` and `App.remote()`, a per-primitive entry adds just the one entry, under its own name with no namespace prefix, and belongs to the app (or server) whose array lists it, so that owner's hooks, plugins and authorities apply. The server loads every entry at startup: each package once and each remote server over one connection, however many entries name it with the same loader or connection options. `options.metadata` overrides the loaded metadata, and an entry the package or server does not have fails startup with a typed error that names it.

<Warning>
`Agent.esm()`, `Agent.remote()`, `Skill.esm()`, `Skill.remote()`, `Job.esm()` and `Job.remote()` are refused at startup with `ExternalEntryNotSupportedError`. Declare agents, skills and jobs locally; see [Agents](/frontmcp/servers/agents), [Skills](/frontmcp/servers/skills) and [Jobs](/frontmcp/servers/jobs) for the alternatives.
</Warning>

<Tip>
Per-primitive loading gives you fine-grained control. Instead of importing an entire package's tools, you can pick exactly the ones you need. See [Tools](/frontmcp/servers/tools#loading-from-npm-or-remote-servers), [Resources](/frontmcp/servers/resources#loading-from-npm-or-remote-servers) and [Prompts](/frontmcp/servers/prompts#loading-from-npm-or-remote-servers) for details.
</Tip>

## Best Practices

**Do:**

- Use descriptive `id` values that work as URL segments
- Group related tools, resources, and prompts in the same app
- Configure `standalone: true` when apps need isolated auth
- Use adapters to generate tools from OpenAPI specs

**Don't:**

- Put unrelated functionality in the same app
- Mix authentication strategies within a single app
- Create apps with only one tool (use the server directly)
- Use `App.esm()` for external MCP servers (use `App.remote()` instead)

**Choosing between app types:**

- **Local `@App`**: First-party code you own and maintain
- **`App.esm()`**: Community or internal packages distributed via npm
- **`App.remote()`**: External MCP servers running as separate processes
