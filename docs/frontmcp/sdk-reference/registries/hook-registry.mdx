## Overview

`HookRegistry` is not exported from `@frontmcp/sdk`: reach a scope's registry through `scope.hooks`. Inside a tool, resource or prompt, `this.scope` is the scope serving the call.

```typescript
// In a tool, resource or prompt
const hooks = this.scope.hooks;

// Get all hooks
const allHooks = hooks.getHooks();

// Get hooks for a specific flow
const toolHooks = hooks.getFlowHooks('tools:call-tool');
```

You do not register hooks through the registry. Declare them with the decorators of the flow (`ToolHook.Will('execute')`, `FlowHooksOf('<flow-name>')`) on a plugin, a provider or an entry class, and the SDK registers them. See [Flow Hooks](/frontmcp/sdk-reference/decorators/hooks).

## Methods

### getHooks()

Get all hooks (instances, unordered).

```typescript
getHooks(): HookEntry[]
```

**Example:**

```typescript
const hooks = registry.getHooks();
for (const hook of hooks) {
  const { flow, type, stage, method } = hook.metadata;
  console.log(`Hook: ${flow} ${type} ${stage} (${method})`);
}
```

### getFlowHooks()

Get the plugin and provider hooks of a flow, sorted by priority (descending).

```typescript
getFlowHooks(flow: FlowName): HookEntry[]
```

**Example:**

```typescript
const hooks = registry.getFlowHooks('tools:call-tool');
// Registry order is highest priority first; within a stage, hooks run lowest priority first
```

### getFlowStageHooks()

Get the plugin and provider hooks on one stage of a flow: its `Will`, `Did`, `Around` and `Stage` hooks alike. `metadata.type` tells them apart.

```typescript
getFlowStageHooks(flow: FlowName, stage: string): HookEntry[]
```

**Example:**

```typescript
const executeHooks = registry.getFlowStageHooks('tools:call-tool', 'execute');
const beforeHooks = executeHooks.filter((hook) => hook.metadata.type === 'will');
const afterHooks = executeHooks.filter((hook) => hook.metadata.type === 'did');
```

### getFlowHooksForOwner()

Get the hooks a flow runs for an entry of the given owner (an app id): hooks with no owner or owned by the scope or a plugin, and the hooks owned by that app. A hook of another app declared with `appliesTo: 'uncovered-apps'` is included when no instance of the same hook applies to the owner. Without `ownerId`, returns every hook of the flow.

```typescript
getFlowHooksForOwner(flow: FlowName, ownerId?: string): HookEntry[]
```

**Example:**

```typescript
// Get the hooks that run for the tools of the 'my-app' app
const appHooks = registry.getFlowHooksForOwner('tools:call-tool', 'my-app');
```

### getClsHooks()

Get the hooks declared on a given entry class (a `@Tool`, `@Resource`, `@Prompt` or `@Agent` class).

```typescript
getClsHooks(token: Token): HookEntry[]
```

**Example:**

```typescript
const classHooks = registry.getClsHooks(MyToolClass);
```

### registerHooks()

Register hook records. The SDK calls it when it sets up plugins, providers and entry classes, with the records it reads from their decorated methods.

```typescript
registerHooks(embedded: boolean, ...records: HookRecord[]): Promise<void[]>
```

| Parameter  | Type           | Description                                                                          |
| ---------- | -------------- | ------------------------------------------------------------------------------------ |
| `embedded` | `boolean`      | `true` for hooks declared on an entry class (indexed by class), `false` for the rest |
| `records`  | `HookRecord[]` | `{ kind: HookKind.METHOD_TOKEN, provide, metadata }`, one per hook method            |

## Hook Structure

A `HookEntry` carries the hook's `metadata`:

```typescript
interface HookMetadata {
  flow: FlowName;                         // Flow name (e.g., 'tools:call-tool')
  stage: string;                          // Stage name (e.g., 'execute')
  type: 'will' | 'did' | 'around' | 'stage';
  method: string;                         // Name of the hook method
  target: Token | null;                   // Instance (or class, for a static hook) the method runs on
  static?: boolean;
  priority?: number;                      // Order within a stage (lower runs first, default 0)
  filter?: (ctx) => boolean | Promise<boolean>;
  appliesTo?: 'own-app' | 'uncovered-apps';
  owner?: EntryOwnerRef;                  // The app, agent, plugin or scope that registered the hook
}
```

## Flow Stages

Each flow declares its own stages. A hook names one of them and runs relative to it by its type: `Will` before the stage, `Did` after it, `Around` wrapping it, and `Stage` as one more step of it, next to the flow's own step (it does not replace it). The stages of `tools:call-tool`, in order:

```
parseInput → ensureRemoteCapabilities → findTool → checkToolAuthorization → checkEntryAuthorities
  → createTaskIfRequested → createToolCallContext → checkToolCredentials → acquireQuota → acquireSemaphore
  → validateInput → execute → validateOutput → releaseSemaphore → releaseQuota → applyUI → finalize
```

There are no `beforeExecute`/`afterExecute` stages: hook `execute` with `Will` or `Did`. When a stage fails, the flow skips the stages after it and runs its cleanup stages (in `tools:call-tool`, `releaseSemaphore`, `releaseQuota`, `applyUI` and `finalize`).

## Priority

The registry lists hooks by priority, highest first. When a flow runs a stage, its hooks run in ascending priority:

```typescript
import { Plugin, ToolHook } from '@frontmcp/sdk';

@Plugin({ name: 'ordering' })
class OrderingPlugin {
  @ToolHook.Will('execute', { priority: 100 })
  runsSecond() {}

  @ToolHook.Will('execute', { priority: 50 })
  runsFirst() {}
}
```

## Embedded vs External Hooks

### Embedded Hooks

Declared on a tool, resource, prompt or agent class with the flow's decorators:

```typescript
import { Tool, ToolContext, ToolHook } from '@frontmcp/sdk';

@Tool({ name: 'my_tool', inputSchema: {} })
class MyTool extends ToolContext {
  @ToolHook.Will('execute')
  beforeExecute() {
    this.logger.info('Before execute');
  }

  async execute() {
    return { ok: true };
  }
}
```

Embedded hooks:

- Are scoped to their class, and run on the instance built for each call
- Use `getClsHooks()` for lookup
- Are registered with `registerHooks(true, ...)`

### External Hooks

Declared on a plugin or a provider:

```typescript
import { FlowCtxOf, Plugin, ToolHook } from '@frontmcp/sdk';

@Plugin({ name: 'audit' })
class AuditPlugin {
  @ToolHook.Did('execute')
  async audit(ctx: FlowCtxOf<'tools:call-tool'>) {
    const { tool, toolContext } = ctx.state.required;
    await auditLog(tool.name, toolContext.output);
  }
}
```

External hooks:

- Can target any flow
- Use `getFlowHooks()` and `getFlowStageHooks()` for lookup
- Are registered with `registerHooks(false, ...)`

## Hook Context

A hook method receives the running flow as its first argument. Type it with `FlowCtxOf<'<flow-name>'>`. An `@Around` hook also receives `next`, which runs the wrapped stage. `this` is the plugin or provider instance the hook is declared on.

```typescript
import { FlowCtxOf, Plugin, ToolHook } from '@frontmcp/sdk';

@Plugin({ name: 'audit' })
class AuditPlugin {
  @ToolHook.Did('execute')
  logResult(ctx: FlowCtxOf<'tools:call-tool'>) {
    const { tool, toolContext } = ctx.state.required;
    ctx.logger.info(`Tool ${tool.name} returned ${JSON.stringify(toolContext.output)}`);
  }
}
```

The flow exposes:

| Member            | Description                                                                                         |
| ----------------- | --------------------------------------------------------------------------------------------------- |
| `state`           | The flow's state, typed per flow (see below)                                                        |
| `rawInput`        | The input the flow was started with; for `tools:call-tool`, the MCP `request` and its `ctx`         |
| `logger`          | The flow's logger (the tool, resource and prompt flows define one; every flow has `scopeLogger`)    |
| `get(token)`      | Resolves a provider registered on the server, or a context-scoped provider of the current run       |
| `respond(output)` | Ends the flow with this output; from `@Will('execute')` on `tools:call-tool`, the tool does not run |
| `fail(error)`     | Ends the flow with this error                                                                       |

Read a state key directly (`ctx.state.tool`, `undefined` until a stage sets it) or through `ctx.state.required` (throws when the key is unset), and write one with `ctx.state.set(key, value)`. For `tools:call-tool` the state holds `input` (the requested tool `name` and its `arguments`), `tool` (the tool entry) and `toolContext` (the tool instance, whose `output` is the tool's result once `execute` ran).

## Index Structure

Unlike other registries, HookRegistry uses specialized indexes:

| Index              | Key                  | Description                   |
| ------------------ | -------------------- | ----------------------------- |
| `recordsByCls`     | `Token`              | Historical records by class   |
| `entriesByCls`     | `Token`              | Hook instances by class       |
| `hooksByFlow`      | `flow`               | Hooks indexed by flow         |
| `hooksByFlowStage` | `flow`, then `stage` | Hooks indexed by flow + stage |
