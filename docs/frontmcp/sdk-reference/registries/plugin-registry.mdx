## Overview

The plugin registry is internal: `PluginRegistry` is not exported from `@frontmcp/sdk`, and `ScopeEntry` does not declare it. At runtime the scope holds the registry of its server-level plugins (`@FrontMcp({ plugins })`) under `plugins`, `undefined` when there are none; plugins installed on an app live in that app's registry, which the scope does not expose. The exported `PluginRegistryInterface` types the part this page describes:

```typescript
import type { PluginRegistryInterface } from '@frontmcp/sdk';

// Access via scope (runtime only: ScopeEntry does not declare `plugins`)
const plugins = (scope as unknown as { plugins?: PluginRegistryInterface }).plugins;

// List all server-level plugins
const allPlugins = plugins?.getPlugins() ?? [];
```

## Methods

### getPlugins()

Get the registered plugin instances: the objects your plugin classes construct. They are typed `PluginEntry`, but a plugin class need not carry `metadata`, so read the names from `getPluginNames()`.

```typescript
getPlugins(): PluginEntry[]
```

**Example:**

```typescript
const cachePlugin = registry.getPlugins().find((plugin) => plugin instanceof CachePlugin);
```

### getPluginNames()

Get the names of the registered plugins, from their `@Plugin` metadata.

```typescript
getPluginNames(): string[]
```

**Example:**

```typescript
console.log(`Plugins: ${registry.getPluginNames().join(', ')}`);
```

## Plugin Architecture

Plugins create nested registries for their components:

```
PluginRegistry
├── pProviders    → Map<Token, ProviderDef>
├── pPlugins      → Map<Token, PluginRegistry>  (nested plugins)
├── pAdapters     → Map<Token, AdapterRegistry>
├── pTools        → Map<Token, ToolRegistry>
├── pResources    → Map<Token, ResourceRegistry>
├── pPrompts      → Map<Token, PromptRegistry>
└── pSkills       → Map<Token, SkillRegistry>
```

For each plugin, the registry works in this order:

1. Build the plugin's own provider registry from `providers`.
2. Create the plugin instance. For `init({ inject, useFactory })`, the factory runs here with dependencies resolved from the host registry.
3. Register the providers derived from the options (`dynamicProviders(options)` and `init({ providers })`).
4. Build the nested `plugins`, adapters, tools, resources, prompts and skills. Nested plugins can inject the providers registered in step 3.
5. Merge `exports` into the host registry, register hooks and context extensions, then merge the option-derived providers into the host registry and the scope registry.

The scope registry keeps only the copy of an option-derived provider from the app that merged last. Tools, resources and prompts resolve their own hierarchy's definition first (see [`buildViews()`](/frontmcp/sdk-reference/registries/provider-registry#buildviews)), so each app still gets its own.

## Plugin Registration

Plugins are registered via the `@FrontMcp` decorator:

```typescript
@FrontMcp({
  info: { name: 'my-server', version: '1.0.0' },
  apps: [MyApp],
  plugins: [
    RememberPlugin,
    CachePlugin,
    MyCustomPlugin,
  ],
})
class MyServer { }
```

Or via the `@Plugin` decorator for custom plugins:

```typescript
@Plugin({
  name: 'my-plugin',
  tools: [CustomTool],
  providers: [CustomProvider],
})
class MyCustomPlugin { }
```

## Hook Registration

Plugins register hooks by declaring them on their methods, and on the methods of their providers, with the flow's decorators. The registry reads them when it creates the plugin; `@Plugin` has no `hooks` option.

```typescript
import { FlowCtxOf, Plugin, ToolHook } from '@frontmcp/sdk';

@Plugin({ name: 'audit-plugin' })
class AuditPlugin {
  @ToolHook.Did('execute')
  async audit(ctx: FlowCtxOf<'tools:call-tool'>) {
    const { tool, toolContext } = ctx.state.required;
    await auditLog(tool.name, toolContext.output);
  }
}
```

Hooks are registered with scope-aware targeting:

- **App-scoped**: Hook applies only to the app's tools, resources, prompts and completions, including those its adapters and plugins provide. Hooks of a plugin nested inside another plugin belong to the app that installed the outer plugin.
- **Server-scoped**: Hook applies to all tools in the server

## Context Extensions

Plugins can extend execution contexts with new properties:

```typescript
// In plugin
declare module '@frontmcp/sdk' {
  interface ExecutionContextBase {
    readonly remember: RememberApi;
  }
}

export function installRememberContextExtension(): void {
  Object.defineProperty(ExecutionContextBase.prototype, 'remember', {
    get: function() {
      return this.get(RememberToken);
    },
  });
}
```

Usage in tools:

```typescript
@Tool({ name: 'my_tool', inputSchema: {} })
class MyTool extends ToolContext {
  async execute() {
    // Plugin-provided context extension
    await this.remember.set('key', 'value');
  }
}
```

## Provider Merging

A plugin's `providers` stay in the plugin's own registry, where its hooks, tools and nested plugins resolve them. The ones it lists in `exports` are merged into the host registry, the app (or server) that installed it, so the host's tools can resolve them with `this.get()`. The providers derived from a dynamic plugin's options (`dynamicProviders(options)` and `init({ providers })`) are merged into the host registry and the scope registry.

A factory provider takes a `provide` token, a `name`, `inject` (the tokens of its dependencies) and a `useFactory`. `scope` is `ProviderScope.GLOBAL` (the default, one instance) or `ProviderScope.CONTEXT` (one per request context). `exports` takes provider definitions, so list the same definition in both arrays:

```typescript
import { Plugin, ProviderScope } from '@frontmcp/sdk';

export const CacheToken = Symbol('Cache');

const cacheProvider = {
  name: 'cache',
  provide: CacheToken,
  inject: () => [],
  useFactory: () => new RedisCache(),
  scope: ProviderScope.GLOBAL,
};

@Plugin({
  name: 'cache-plugin',
  providers: [cacheProvider],
  exports: [cacheProvider],
})
class CachePlugin { }
```
