## Overview

```typescript
import { PluginRegistry } from '@frontmcp/sdk';

// Access via scope
const plugins = scope.plugins;

// List all plugins
const allPlugins = plugins.getPlugins();
```

## Methods

### getPlugins()

Get all registered plugins.

```typescript
getPlugins(): ReadonlyArray<PluginEntry>
```

**Example:**

```typescript
const plugins = registry.getPlugins();
for (const plugin of plugins) {
  console.log(`Plugin: ${plugin.name}`);
}
```

## Plugin Architecture

Plugins create nested registries for their components:

```
PluginRegistry
├── pProviders    → Map<Token, ProviderDef>
├── pPlugins      → Map<Token, PluginRegistry>  (nested plugins)
├── pAdapters     → Map<Token, AdapterRegistry>
├── pTools        → Map<Token, ToolRegistry>
├── pResources    → Map<Token, ResourceRegistry>
├── pPrompts      → Map<Token, PromptRegistry>
└── pSkills       → Map<Token, SkillRegistry>
```

For each plugin, the registry works in this order:

1. Build the plugin's own provider registry from `providers`.
2. Create the plugin instance. For `init({ inject, useFactory })`, the factory runs here with dependencies resolved from the host registry.
3. Register the providers derived from the options (`dynamicProviders(options)` and `init({ providers })`).
4. Build the nested `plugins`, adapters, tools, resources, prompts and skills. Nested plugins can inject the providers registered in step 3.
5. Merge `exports` into the host registry, register hooks and context extensions, then merge the option-derived providers into the host registry and the scope registry.

The scope registry keeps only the copy of an option-derived provider from the app that merged last. Tools, resources and prompts resolve their own hierarchy's definition first (see [`buildViews()`](/frontmcp/sdk-reference/registries/provider-registry#buildviews)), so each app still gets its own.

## Plugin Registration

Plugins are registered via the `@FrontMcp` decorator:

```typescript
@FrontMcp({
  name: 'my-server',
  plugins: [
    RememberPlugin,
    CachePlugin,
    MyCustomPlugin,
  ],
})
class MyServer { }
```

Or via the `@Plugin` decorator for custom plugins:

```typescript
@Plugin({
  name: 'my-plugin',
  tools: [CustomTool],
  providers: [CustomProvider],
})
class MyCustomPlugin { }
```

## Hook Registration

Plugins can register hooks that run during tool/resource/prompt flows:

```typescript
@Plugin({
  name: 'audit-plugin',
  hooks: [
    {
      flow: 'tools:call-tool',
      stage: 'afterExecute',
      handler: async (ctx) => {
        await auditLog(ctx.toolName, ctx.result);
      },
    },
  ],
})
class AuditPlugin { }
```

Hooks are registered with scope-aware targeting:

- **App-scoped**: Hook applies only to the app's tools, resources, prompts and completions, including those its adapters and plugins provide. Hooks of a plugin nested inside another plugin belong to the app that installed the outer plugin.
- **Server-scoped**: Hook applies to all tools in the server

## Context Extensions

Plugins can extend execution contexts with new properties:

```typescript
// In plugin
declare module '@frontmcp/sdk' {
  interface ExecutionContextBase {
    readonly remember: RememberApi;
  }
}

export function installRememberContextExtension(): void {
  Object.defineProperty(ExecutionContextBase.prototype, 'remember', {
    get: function() {
      return this.get(RememberToken);
    },
  });
}
```

Usage in tools:

```typescript
@Tool({ name: 'my_tool', inputSchema: {} })
class MyTool extends ToolContext {
  async execute() {
    // Plugin-provided context extension
    await this.remember.set('key', 'value');
  }
}
```

## Provider Merging

Plugin providers are merged into both:

- App registry (for app-scoped access)
- Scope registry (for server-wide access)

```typescript
@Plugin({
  name: 'cache-plugin',
  providers: [
    {
      token: CacheToken,
      useFactory: () => new RedisCache(),
      scope: ProviderScope.SINGLETON,
    },
  ],
})
class CachePlugin { }
```
