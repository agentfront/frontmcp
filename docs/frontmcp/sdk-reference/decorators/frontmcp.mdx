## Basic Usage

```typescript
import { FrontMcp } from '@frontmcp/sdk';

@FrontMcp({
  info: { name: 'My Server', version: '1.0.0' },
  apps: [MyApp],
})
export default class MyServer {}
```

## Signature

```typescript
function FrontMcp(providedMetadata: FrontMcpMetadata): ClassDecorator
```

## Configuration Options

### Required Properties

| Property | Type                | Description                                                                      |
| -------- | ------------------- | -------------------------------------------------------------------------------- |
| `info`   | `ServerInfoOptions` | Server metadata (`name`, `version`, and optional `title`, `websiteUrl`, `icons`) |
| `apps`   | `AppType[]`         | Array of app classes to register                                                 |

`info` is the `serverInfo` of every `initialize` response, `title`, `websiteUrl` and `icons` included; without a `title`,
`serverInfo.title` is the `name`. Up to 1.9.2, `serverInfo.title` was always the `name`. The `instructions` below reach
every transport's `initialize`, `createFetchHandler()` and `connect()` included; up to 1.9.2 those two sent none.

### Server Metadata

| Property       | Type     | Default | Description                                                                                                                                                                                                         |
| -------------- | -------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `instructions` | `string` | `''`    | Top-level server-level instructions surfaced as `instructions` in the MCP `initialize` response. See [Skill catalog injection](#skill-catalog-injection) for how it combines with `skillsConfig.injectInstructions` |

### Server Configuration

| Property | Type               | Default | Description               |
| -------- | ------------------ | ------- | ------------------------- |
| `serve`  | `boolean`          | `true`  | Auto-start HTTP server    |
| `http`   | `HttpOptionsInput` | -       | HTTP server configuration |

<Warning>
With `serve: true` (the default), the decorated server **starts when its module
is imported**. To serve over **stdio** instead — with no HTTP port bound — set
`FRONTMCP_STDIO=1` before the module loads; the decorator then connects the
stdio transport rather than starting HTTP. The built `--stdio` runner and
`--target cli` binaries set this flag for you. Set `serve: false` to opt out of
auto-starting entirely (use `FrontMcpInstance.bootstrap`/`runStdio` explicitly).
</Warning>

```typescript
@FrontMcp({
  info: { name: 'My Server', version: '1.0.0' },
  apps: [MyApp],
  serve: true,
  http: {
    port: 3000,
    cors: { origin: '*' },
  },
})
```

`http.hostFactory` replaces the default Express host with a `FrontMcpServer` of your own, or a function that builds one from the HTTP options.

### Storage Configuration

| Property | Type                 | Description                      |
| -------- | -------------------- | -------------------------------- |
| `redis`  | `RedisOptionsInput`  | Redis storage for sessions/state |
| `pubsub` | `PubsubOptionsInput` | Pub/Sub for distributed events   |

```typescript
@FrontMcp({
  info: { name: 'My Server', version: '1.0.0' },
  apps: [MyApp],
  redis: {
    provider: 'redis',
    host: 'localhost',
    port: 6379,
    keyPrefix: 'mcp:',
  },
})
```

`redis` (and `pubsub`) also take a connection URL — `redis: { url: process.env.REDIS_URL }` — which is read into `host`/`port`/`password`/`db` (`rediss://` sets `tls`). Fields beside the `url` only fill in what it leaves out; one that contradicts it is a validation error. See [Redis Setup](/frontmcp/deployment/redis-setup).

### Transport Configuration

| Property    | Type                    | Description                |
| ----------- | ----------------------- | -------------------------- |
| `transport` | `TransportOptionsInput` | Session lifecycle settings |

```typescript
@FrontMcp({
  info: { name: 'My Server', version: '1.0.0' },
  apps: [MyApp],
  redis: { provider: 'redis', host: 'localhost', port: 6379 },
  transport: {
    distributedMode: true,
    persistence: { defaultTtlMs: 3600000 }, // keep session metadata for 1 hour
  },
})
```

### Shared Components

| Property     | Type             | Description                                                                                        |
| ------------ | ---------------- | -------------------------------------------------------------------------------------------------- |
| `providers`  | `ProviderType[]` | Gateway-level providers                                                                            |
| `tools`      | `ToolType[]`     | Tools every app serves — see [Server-level tools and resources](#server-level-tools-and-resources) |
| `resources`  | `ResourceType[]` | Resources and resource templates every app serves                                                  |
| `skills`     | `SkillType[]`    | Shared skills                                                                                      |
| `plugins`    | `PluginType[]`   | Server-level plugins                                                                               |
| `adapters`   | `AdapterType[]`  | Server-level adapters: the tools, resources and prompts they fetch serve every app                 |
| `splitByApp` | `boolean`        | Run each app as an isolated sub-server                                                             |

<Note>
Prompts, agents, jobs, workflows, and channels are declared at the `@App` level — not at the gateway level. See the [@App reference](/frontmcp/sdk-reference/decorators/app) for the full list.
</Note>

```typescript
@FrontMcp({
  info: { name: 'My Server', version: '1.0.0' },
  apps: [MyApp],
  providers: [ConfigService, LoggingService],
  plugins: [RememberPlugin, CachePlugin],
  tools: [HealthCheckTool],
})
```

#### Server-level tools and resources

Tools, resources and resource templates declared on `@FrontMcp` are listed, called and read next to every app's own, through the same flows: hooks of server-level plugins, hooks declared on the entry class, `authorities`, rate limits, `availableWhen`, and the startup checks apply to them as they do to app entries. They resolve the server-level `providers`, not an app's.

- **Every scope serves them.** With `splitByApp: true`, and for a `standalone` app, each app's scope builds its own instance of every server-level tool and resource, as it does for server-level plugins and adapters.
- **Name conflicts.** A server-level tool keeps its name unless an app in the same scope has a tool of that name. Then both are prefixed with their owner: `<app id>:<name>` for the app's tool and `server:<name>` for the server's. Call each by the name `tools/list` returns. For that reason no app may have the id `server` while `@FrontMcp` declares tools or resources; startup fails with `ReservedAppIdError`.
- **Plugins.** An app's plugin hooks run for a server-level tool only when declared with `appliesTo: 'uncovered-apps'`; server-level plugin hooks always run.
- **Progressive authorization.** A server-level tool belongs to no app, so `incrementalAuth` does not ask for an app grant before it runs.

`@FrontMcp` does not accept `prompts`; declare them on an `@App`, or serve them from a server-level adapter or plugin.

```typescript
  },

```

## Full Example

```typescript
import { FrontMcp, App, LogLevel, Tool, ToolContext } from '@frontmcp/sdk';
import { RememberPlugin } from '@frontmcp/plugin-remember';
import { z } from '@frontmcp/sdk';

@Tool({
  name: 'greet',
  inputSchema: { name: z.string() },
})
class GreetTool extends ToolContext {
  async execute(input: { name: string }) {
    return `Hello, ${input.name}!`;
  }
}

@App({
  name: 'main',
  tools: [GreetTool],
})
class MainApp {}

@FrontMcp({
  info: {
    name: 'Greeting Server',
    version: '1.0.0',
    title: 'A simple greeting MCP server',
  },
  apps: [MainApp],
  serve: true,
  http: { port: 3000 },
  plugins: [RememberPlugin],
  logging: { level: LogLevel.Info },
})
export default class GreetingServer {}
```

## Skill catalog injection

The optional `skillsConfig.injectInstructions` field controls how the server's auto-built skill catalog summary is merged into the `instructions` field on the MCP `initialize` response, and on the `server/discover` result for MCP 2026-07-28 clients (up to 1.9.2 `server/discover` sent the server's `instructions` alone, without the channel hint or the catalog).

| Mode      | Behavior                                                                                                                                                 |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `off`     | The skill catalog summary is suppressed. `instructions` and channel hints are still sent.                                                                |
| `append`  | `instructions`, then channel hints, then the skill catalog summary, joined by a separator. **(Default.)**                                                |
| `prepend` | The skill catalog summary first, then channel hints, then `instructions`.                                                                                |
| `replace` | Only `instructions` is sent; the catalog summary and channel hints are dropped. Falls back to `append` when `instructions` is empty, so nothing is lost. |

The summary is generated by `composeInitializeInstructions(...)` and `buildSkillsCatalogSummary(...)` (exported from `@frontmcp/sdk`). It is bounded at **16 KB** with a truncation footer. Its header and footer point clients at the SEP-2640 `skill://index.json` resource, which lists each skill's `SKILL.md` URI. With `skillsConfig.mcpResources: false` no `skill://` resource is served, so they point at the `skills/load` and `skills/search` methods instead. The composer is re-evaluated on every `initialize` request, so skills registered dynamically after server boot are picked up automatically.

The catalog is composed for the client that initializes, like `skills/list`: it only names skills whose `authorities` that caller satisfies and that the hookable `skills:filter` flow keeps (a skill whose feature flag is off, for one). The SEP-2640 `skill://` hints added under `skillsConfig.sep2640InInstructions` follow the same rule. When nothing gates a skill, the instructions are unchanged. The transports use `composeCallerInstructions(scope, { ctx })`, also exported from `@frontmcp/sdk`, for embedders that build their own `initialize` response.

```typescript
@FrontMcp({
  info: { name: 'my-server', version: '1.0.0' },
  apps: [MainApp],
  instructions: 'You are a helpful assistant for booking flights.',
  skillsConfig: {
    enabled: true,
    injectInstructions: 'append',
  },
})
class Server {}
```

## Audit log

`skillsConfig.audit` enables a tamper-evident, hash-chained audit log of skill action executions (authority pass / authority fail / HTTP success / HTTP failure phases). Records are signed and chained so that any later mutation breaks verification.

| Field                  | Type                          | Default   | Description                                                                                                         |
| ---------------------- | ----------------------------- | --------- | ------------------------------------------------------------------------------------------------------------------- |
| `enabled`              | `boolean`                     | `false`   | Turn the audit writer on                                                                                            |
| `signer`               | `SkillAuditSigner`            | dev HS256 | Signs each record. Use `Rs256AuditSigner` in production; without a signer the server refuses to start in production |
| `store`                | `SkillAuditStore`             | memory    | Where records are persisted. Use `StorageAdapterAuditStore` for Redis/Vercel KV/SQLite-backed storage               |
| `metrics`              | `SkillAuditMetrics`           | unset     | Counts failed and dropped writes. Build it with `createSkillAuditMetrics({ createCounter })`                        |
| `subjectMode`          | `'plain' \| 'hash' \| 'omit'` | `'hash'`  | Redaction policy for the principal embedded in each record                                                          |
| `headAnchorIntervalMs` | `number`                      | unset     | Reserved for head anchoring. Validated, but not read yet                                                            |

The audit module lives in `@frontmcp/adapters/skills`, which the SDK does not import: register it once at boot with `setSkillAuditFactory(() => auditModule)`. See the [skill audit log extensibility page](/frontmcp/extensibility/skill-audit-log) for the full architecture, threat model, and chain verification recipe.

```typescript
import * as auditModule from '@frontmcp/adapters/skills';
import { createSkillAuditMetrics, Rs256AuditSigner, StorageAdapterAuditStore } from '@frontmcp/adapters/skills';
import { createCounter } from '@frontmcp/observability';
import { FrontMcp, setSkillAuditFactory } from '@frontmcp/sdk';
import { createStorage } from '@frontmcp/utils';

import { MainApp } from './main.app';

setSkillAuditFactory(() => auditModule);

const privateJwkJson = process.env.BUNDLE_SIGNING_PRIVATE_JWK;
if (!privateJwkJson) throw new Error('BUNDLE_SIGNING_PRIVATE_JWK is not set');
const storage = await createStorage({ type: 'redis', redis: { config: { host: 'localhost', port: 6379 } } });

@FrontMcp({
  info: { name: 'prod-server', version: '1.0.0' },
  apps: [MainApp],
  skillsConfig: {
    enabled: true,
    audit: {
      enabled: true,
      signer: new Rs256AuditSigner(JSON.parse(privateJwkJson) as JsonWebKey, 'bundle-signing-2026-01'),
      store: new StorageAdapterAuditStore(storage),
      metrics: createSkillAuditMetrics({ createCounter }),
      subjectMode: 'hash',
    },
  },
})
class ProdServer {}
```

<Note>
The writer is **single-writer only**: it serializes writes within one process, but two pods appending to the same store can link their records to the same tail, which `verifyChain` reports as a `prevHash` mismatch. Route audit writes to a single elected leader pod, or use per-pod chains and stitch them offline.
</Note>

## Bootstrap Methods

### HTTP Server

```typescript
import { FrontMcpInstance } from '@frontmcp/sdk';
import config from './server';

// Start HTTP server
await FrontMcpInstance.bootstrap(config);
```

### Serverless Handler

```typescript
import { FrontMcpInstance } from '@frontmcp/sdk';
import config from '../src/server';

// Export for Vercel/AWS Lambda
export default FrontMcpInstance.createHandler(config);
```

### Stdio Transport

```typescript
import { FrontMcpInstance } from '@frontmcp/sdk';
// Import the config object, NOT the @FrontMcp-decorated class — importing the
// decorated class would auto-start an HTTP server alongside stdio.
import { serverConfig } from './server-config';

// Connect via stdio (for Claude Desktop). Binds no HTTP port.
await FrontMcpInstance.runStdio(serverConfig);
```

### Direct Client

```typescript
import { FrontMcpInstance } from '@frontmcp/sdk';
import config from './server';

// Create direct programmatic access
const server = await FrontMcpInstance.createDirect(config);
const tools = await server.listTools();
```
