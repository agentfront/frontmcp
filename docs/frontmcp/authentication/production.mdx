Before deploying FrontMCP authentication to production, review this comprehensive checklist covering security, configuration, and operational requirements.

## Pre-Deployment Checklist

<Steps>
  <Step title="Configure Persistent Token Storage">
    Replace in-memory storage with a persistent store. Use **Redis** for multi-instance deployments, or **SQLite** for a single-instance/single-node deployment that needs tokens to survive a restart.

    ```typescript
    // Redis — shared across instances
    auth: {
      mode: 'local',
      tokenStorage: {
        redis: {
          host: process.env.REDIS_HOST!,
          port: parseInt(process.env.REDIS_PORT || '6379'),
          password: process.env.REDIS_PASSWORD,
          tls: true,
        },
      },
    }
    ```

    ```typescript
    // SQLite — single-instance persistence (not shared across nodes)
    auth: {
      mode: 'local',
      tokenStorage: {
        sqlite: {
          path: process.env.AUTH_DB_PATH ?? './data/auth.sqlite',
          encryption: { secret: process.env.AUTH_DB_SECRET! },
        },
      },
    }
    ```

    <Note>
      SQLite persists tokens on the local disk of one node — it is **not** a shared store. For more than one instance behind a load balancer, use Redis so every instance reads the same authorization/refresh/session state.
    </Note>

  </Step>

  <Step title="Provide a Persistent Signing Secret">
    `local` and `remote` mode sign their tokens with HS256 using `JWT_SECRET` (at least 32 bytes; production refuses
    to start without it). It also encrypts the stored upstream provider tokens. Without it, a random per-process secret
    is used, so tokens die on every restart. Give every instance the same value.

    ```bash
    JWT_SECRET=$(openssl rand -hex 32)
    ```

    <Note>
      `local.signKey` and `local.jwks` (and public mode's `signKey` and `jwks`) are accepted but not used yet: tokens
      are always signed with `JWT_SECRET`.
    </Note>

  </Step>

  <Step title="Enable Refresh Token Flow">
    For `local` and `remote` modes, upstream provider tokens (`this.orchestration.getToken`) are renewed with the provider's refresh token when they expire, `skewSeconds` early. It is on by default; `enabled: false` turns it off.

    ```typescript
    auth: {
      refresh: {
        enabled: true,
        skewSeconds: 60, // renew upstream tokens this many seconds before expiry
      },
    }
    ```

    In both **local** and **remote** mode FrontMCP is the authorization server for its clients: it mints its own access tokens (HS256-signed with `JWT_SECRET`, valid for an hour) and refresh tokens (30 days, rotated on each use). In **remote** mode the upstream identity provider controls only the lifetime of its own tokens, the provider tokens tools read through `this.orchestration`, which `refresh` renews.

  </Step>

  <Step title="Enable HTTPS">
    All production traffic must use TLS. Configure your reverse proxy or load balancer.
  </Step>

  <Step title="Set Expected Audience">
    Validate the audience (`aud`) claim. In **transparent** mode set `expectedAudience`. In **local** and **remote** mode the tokens FrontMCP issues always name this server's resource URL as `aud` and name this server as `iss`, and are refused anywhere else, even by a server with the same `JWT_SECRET`; pin `FRONTMCP_PUBLIC_URL` so that URL doesn't come from the `Host` header. Setting `expectedAudience` there too makes the server accept only tokens issued for the listed resource URLs, whatever URL the request arrived at.

    ```typescript
    auth: {
      mode: 'transparent', // also valid for mode: 'local' | 'remote'
      expectedAudience: 'https://api.yourservice.com',
    }
    ```

  </Step>
</Steps>

## Security Requirements

### Required

<Check>**HTTPS only** - Never expose auth endpoints over HTTP in production</Check>
<Check>**Persistent token storage** - Redis with TLS for multi-instance deployments</Check>
<Check>**Stable signing keys** - Provide keys via environment or secrets manager</Check>
<Check>**PKCE enforcement** - OAuth 2.1 requires PKCE (S256 only)</Check>
<Check>**Refresh token rotation** - Always rotate refresh tokens on use</Check>
<Check>**Audience validation** - Validate the `aud` claim via `expectedAudience` in transparent mode; local and remote tokens are bound to this server's resource URL automatically, or to the `expectedAudience` you list</Check>
<Check>**Pinned public URL** - Set `FRONTMCP_PUBLIC_URL` to a fixed origin. The issuer / resource / OAuth-discovery URLs — and the expected audience of a token — are otherwise derived from request headers. `X-Forwarded-Host`/`X-Forwarded-Proto` are **ignored by default**; only enable them with `FRONTMCP_TRUST_PROXY=1` behind a proxy that strips client-supplied forwarded headers. The Web fetch handler (`createFetchHandler`, Workers, Deno, Bun) takes the address from the request URL the runtime hands it, never from a `Host` header that disagrees with it.</Check>

### Recommended

<Check>**Machine ID** - Set `MACHINE_ID` env var for multi-instance session portability</Check>
<Check>**Require registered clients** - Keep `auth.requireRegisteredClients` at its default (`true`, local/remote) so every OAuth client must be registered (DCR / pre-registered) or use a CIMD client-id URL. This enforces exact `redirect_uri` matching and prevents auth-code interception via an unregistered client's attacker-chosen redirect_uri. In production, remote mode admits only CIMD clients (it has no pre-registered clients and DCR is off); see [MCP client registration](/frontmcp/authentication/remote#mcp-client-registration).</Check>

<Check>**Grant only the scopes you mean to** - List your scopes in `auth.allowedScopes` (local/remote); a client that asks for anything else doesn't get it.</Check>
<Check>**Confidential clients** - Clients registered with `client_secret_basic`/`client_secret_post` are authenticated with a constant-time secret check on both the code-exchange and refresh grants.</Check>
<Check>**Rate limiting** - Protect token endpoints from brute force</Check>
<Check>**Monitoring** - Alert on auth failures, unusual patterns</Check>
<Check>**Secret rotation** - Rotate `JWT_SECRET` periodically, knowing it signs clients out</Check>
<Check>**Scope minimization** - Request only necessary scopes</Check>
<Check>**Consent UI** - Let users see what they're authorizing</Check>

## Configuration Reference

### Minimum Production Configuration

```typescript
import { FrontMcp } from '@frontmcp/sdk';

@FrontMcp({
  info: { name: 'ProductionServer', version: '1.0.0' },
  auth: {
    mode: 'local',
    // Persistent storage
    tokenStorage: {
      redis: {
        host: process.env.REDIS_HOST!,
        port: parseInt(process.env.REDIS_PORT || '6379'),
        password: process.env.REDIS_PASSWORD,
        tls: true,
        keyPrefix: 'auth:',
      },
    },

    // Tokens are HS256-signed with the JWT_SECRET environment variable

    // Token refresh settings
    refresh: {
      enabled: true,
      skewSeconds: 60,
    },

    // Security
    consent: { enabled: true },
  },
})
export class Server {}
```

### Environment Variables

```bash
# Required for Redis
REDIS_HOST=redis.example.com
REDIS_PORT=6379
REDIS_PASSWORD=your-redis-password

# Required for token signing (HS256, at least 32 bytes)
JWT_SECRET=your-64-hex-character-secret

# Pin the canonical public origin (issuer / resource / discovery / audience are
# derived from it instead of request headers). Strongly recommended.
FRONTMCP_PUBLIC_URL=https://mcp.example.com

# Only when behind a reverse proxy that STRIPS client-supplied X-Forwarded-*
# headers and sets its own — otherwise these headers are ignored (secure default).
# Prefer FRONTMCP_PUBLIC_URL over trusting the proxy.
# FRONTMCP_TRUST_PROXY=1

# For remote/transparent mode
IDP_PROVIDER_URL=https://auth.example.com
IDP_CLIENT_ID=your-client-id
IDP_CLIENT_SECRET=your-client-secret
IDP_EXPECTED_AUDIENCE=https://api.yourservice.com
```

## Token Lifetime Guidelines

| Environment   | Access Token | Refresh Token | Rationale                |
| ------------- | ------------ | ------------- | ------------------------ |
| Development   | 1 hour       | 7 days        | Developer convenience    |
| Staging       | 30 min       | 7 days        | Balance testing/security |
| Production    | 15 min       | 7-30 days     | Security with usability  |
| High Security | 5 min        | 1 day         | Minimize exposure window |

<Tip>
  Shorter access tokens improve security but increase refresh frequency. Monitor your refresh token endpoint load.
</Tip>

## Key Management

### Signing Secret

Tokens are HS256-signed with `JWT_SECRET`. Generate it with `openssl rand -hex 32` and keep it in your secret manager.
Rotating it invalidates every access token signed with the old value, and the upstream provider tokens stored under it:
clients sign in again (see [Token & Sessions](/frontmcp/authentication/token)).

`local.signKey` and `local.jwks`, meant for asymmetric signing with a key rollover, are accepted but not used yet.

## Redis Configuration

### Secure Redis Connection

```typescript
tokenStorage: {
  redis: {
    host: 'redis.example.com',
    port: 6379,
    password: process.env.REDIS_PASSWORD,
    tls: true,
    keyPrefix: 'frontmcp:auth:',
  },
}
```

### Redis Data Stored

| Key Pattern               | Data                  | TTL          |
| ------------------------- | --------------------- | ------------ |
| `{prefix}pending:{id}`    | Pending authorization | 10 min       |
| `{prefix}code:{code}`     | Authorization code    | 60 sec       |
| `{prefix}refresh:{token}` | Refresh token         | 7-30 days    |
| `{prefix}session:{id}`    | Session data          | Configurable |
| `{prefix}vault:{session}` | Token vault           | Session TTL  |

## Monitoring & Alerting

### Key Metrics to Monitor

| Metric                  | Alert Threshold | Description             |
| ----------------------- | --------------- | ----------------------- |
| Auth failures/min       | > 100           | Possible brute force    |
| Token refresh rate      | > 10x normal    | Possible token theft    |
| JWKS fetch errors       | Any             | IdP connectivity issue  |
| Redis connection errors | Any             | Storage unavailable     |
| Token issuance latency  | > 500ms         | Performance degradation |

### Logging Configuration

```typescript
import { FrontMcp, LogLevel } from '@frontmcp/sdk';

@FrontMcp({
  info: { name: 'Server', version: '1.0.0' },
  logging: {
    level: LogLevel.Info,
  },
  // Redaction is an OBSERVABILITY concern — `logging` has no `redact` field.
  // Configure `redactFields` under observability.logging to strip secrets from
  // structured logs (requires the @frontmcp/observability integration).
  observability: {
    logging: {
      redactFields: ['access_token', 'refresh_token', 'client_secret'],
    },
  },
})
export class Server {}
```

## Common Production Issues

<AccordionGroup>
  <Accordion title="Tokens invalid after deployment">
    **Cause:** Auto-generated keys changed after restart.

    **Solution:** Set `JWT_SECRET` to the same value on every instance and across restarts:
    ```bash
    JWT_SECRET=$(openssl rand -hex 32)
    ```

  </Accordion>

  <Accordion title="Session not found errors across instances">
    **Cause:** Using in-memory storage with multiple instances.

    **Solution:** Configure shared Redis storage:
    ```typescript
    tokenStorage: {
      redis: {
        host: process.env.REDIS_HOST!,
        port: parseInt(process.env.REDIS_PORT || '6379'),
        password: process.env.REDIS_PASSWORD,
        tls: true,
      },
    }
    ```

    **Also check `MCP_SESSION_SECRET`:** it must be the same on every instance. A session id minted under a different secret is answered with HTTP 404 (`-32000`) and the client re-initializes — in every auth mode, including `public`, where the id is the caller's only credential. The same happens once, by design, right after you rotate the secret.

  </Accordion>

  <Accordion title="A 2026-07-28 tool asks its first question again">
    **Cause:** `requestState` is signed with `VAULT_SECRET`, else `JWT_SECRET`, else a random per-process key. With the per-process key, a round answered on another instance (or after a restart) fails verification (`mcp-20260728: rejected requestState`, `reason: 'bad-signature'`, with a `hint` naming `VAULT_SECRET`) and the exchange restarts.

    **Solution:** Set `VAULT_SECRET` (or `JWT_SECRET`) to the same value on every instance. In production, a server with `redis` or `transport.persistence` but neither secret warns about this at startup.

  </Accordion>

  <Accordion title="JWKS fetch fails intermittently">
    **Cause:** Network issues or IdP rate limiting.

    **Solution:**
    - Increase JWKS cache TTL
    - Consider inline JWKS for critical IdPs
    - Add retry logic with exponential backoff

  </Accordion>

  <Accordion title="High latency on token endpoint">
    **Cause:** Redis connection issues or key generation overhead.

    **Solution:**
    - Use Redis connection pooling
    - Pre-generate signing keys (don't generate on-demand)
    - Monitor Redis latency

  </Accordion>
</AccordionGroup>

## Security Hardening

### Disable Insecure Options

```typescript
auth: {
  mode: 'local',

  // Production settings
  allowDefaultPublic: false,   // No anonymous access

  // Use local mode login page or remote IdP
  // Never use the demo login page in production
}
```

For remote mode, DCR is configured under `providerConfig`:

```typescript
auth: {
  mode: 'remote',
  provider: 'https://auth.example.com',
  clientId: process.env.IDP_CLIENT_ID!,
  clientSecret: process.env.IDP_CLIENT_SECRET!,
  providerConfig: {
    dcrEnabled: false,  // Disable DCR in production; pre-register clients
  },
}
```

### HTTP Security Headers

Configure your reverse proxy to add security headers:

```nginx
# Example nginx configuration
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
add_header X-Content-Type-Options "nosniff" always;
add_header X-Frame-Options "DENY" always;
add_header Content-Security-Policy "default-src 'self'" always;
```

### Rate Limiting

FrontMCP includes a built-in **session rate limiter** with a sliding window algorithm:

| Setting          | Default                                            | Description                         |
| ---------------- | -------------------------------------------------- | ----------------------------------- |
| Window           | 60 seconds (`windowMs: 60000`)                     | Sliding window duration             |
| Max requests     | 100 (`maxRequests`)                                | Maximum requests per window per key |
| Cleanup interval | 60000 ms (`cleanupIntervalMs`, set `0` to disable) | Auto-cleanup of expired entries     |

The rate limiter tracks requests per key (typically client IP) and provides:

- `wouldAllow(key)` — pre-check without consuming quota
- `getStats()` — monitoring statistics

For external rate limiting on the token endpoint:

```nginx
# Rate limit token endpoint
location /oauth/token {
    limit_req zone=token_limit burst=10 nodelay;
    proxy_pass http://backend;
}
```

## Deployment Patterns

<Tabs>
  <Tab title="Single Instance">
    ```typescript
    // Simple deployment - in-memory works but not recommended
    auth: {
      tokenStorage: 'memory', // Data lost on restart
    }
    ```

    <Warning>
      In-memory storage loses all sessions on restart. Users must re-authenticate.
    </Warning>

  </Tab>

  <Tab title="Multi-Instance">
    ```typescript
    // Required for horizontal scaling
    auth: {
      tokenStorage: {
        redis: {
          host: process.env.REDIS_HOST!,
          port: parseInt(process.env.REDIS_PORT || '6379'),
          password: process.env.REDIS_PASSWORD,
          tls: true,
        },
      },
    }
    ```

    All instances must share the same Redis and signing keys.

    <Info>
      **Machine ID**: Set the `MACHINE_ID` environment variable to the same value on all instances. Without it, sessions encrypted on one instance cannot be decrypted on another. See [Machine ID](/frontmcp/deployment/machine-id).
    </Info>

  </Tab>

  <Tab title="Stateless">
    ```typescript
    // No shared state needed - tokens contain all info; every instance shares JWT_SECRET
    auth: {
      mode: 'local',
    }
    ```

    Simpler architecture but larger tokens, no silent refresh.

  </Tab>
</Tabs>

## Quick Reference

### OAuth 2.1 Compliance Checklist

<Check>PKCE required for all clients (S256 only)</Check>
<Check>Refresh token rotation enabled</Check>
<Check>No implicit grant flow</Check>
<Check>Authorization codes single-use</Check>
<Check>Redirect URI exact match</Check>
<Check>State parameter required</Check>

### Pre-Production Verification

```bash
# Test token endpoint
curl -X POST https://your-server/oauth/token \
  -d "grant_type=authorization_code" \
  -d "code=test-code" \
  -d "client_id=your-client" \
  -d "code_verifier=verifier"

# Verify JWKS endpoint
curl https://your-server/.well-known/jwks.json

# Check server metadata
curl https://your-server/.well-known/oauth-authorization-server
```
